# FP-RISC 0.14.0 release

Published 15 November 2026: [v0.14.0](https://github.com/hyperswine/fprisc/releases/tag/v0.14.0), a macOS ARM64
archive of 283 commits since 0.13.1. The `fprmeta` index does not offer it yet (see [the index](#the-index)).

The archive was built from clean revision `566870c3` and has SHA256
`51567d1ecb8af4d4c3291dec47e23c5fafe0c13c526de98bc0ff2fb2ae72f59e` (22,087,844 bytes). It includes the compiler, Sol,
the libraries and native dependency notices for 35 packages; non-system dynamic libraries are bundled and relocated.
It requires macOS 27.2 or later, and Apple's Command Line Tools for native builds.

## What is in it

The main subject is generated-code and runtime overhead. On the eight Benchmarks Game programs of `tests/bench/clbg`
the geometric mean of FP-RISC over C went from 6.3x when the suite was first measured to 2.4x at this release (Apple
M4). The three records of 15 November give the changes and the measurements:
[vector views and buffered output](2026-11-15-VECTOR-VIEWS-BUFFERED-OUTPUT.md),
[typed vector reads](2026-11-15-TYPED-VECTOR-READS-FLAT-TABLE.md) and [calls inside loops](2026-11-15-LOOP-CALLS.md).

Sol reports 0.14.0 (it was `0.14.0-dev` on `main`).

## A fix the packaging found

`std/order` has compared Strings with the `strCompare` primitive since 14 November. The Sol interpreter had no such
primitive, so every Sol script that loads `std/order` (the CLI library, and through it the packaging tools) failed to
type-check with the in-tree Sol. The checks did not see it because `tests/run.sol` runs under the installed Sol 0.13.1.
`strCompare` is now in Sol's type environment, arity table and interpreter (`566870c3`).

## Qualification

- `make unit-tests` passes at the version commit.
- `sol tests/run.sol --jobs 3` at `031be2f9`, the commit before the version change: 18 checks, 1 unexpected,
  `result-sizes`, which the installed Sol rejects on its own safety rule and which failed the same way before.
- The archive, extracted to a path containing spaces and run with `HOME` empty and only the archive's `bin`,
  `/usr/bin` and `/bin` on the path (no GHC, Cabal or Homebrew): `fpr --version` and `sol --version` report 0.14.0;
  a program builds and runs, and runs through `fpr run`; `fpr new` then `fpr test` passes; `--target=macos-x86_64`
  builds an x86-64 binary that runs under Rosetta; a Sol script using `std/order` runs; nbody's output matches
  `expected/`; `tests/std/loopcalls` matches its golden output; none of the 11 Mach-O files names a Homebrew or
  `/usr/local` library.
- The download from the release page has the SHA256 above.

Not run: the 51-step installed-toolchain script used for 0.13.1 (it was retired with the Python tooling on
13 November and has no Sol successor), the manager contract groups, and a fresh install through `fprmeta`.
Linux, RISC-V boards and QOS were not qualified against this release.

## The index

The signed `fprmeta` index (`docs/release-indexes/fprisc.json` and its `.sig`, published in the Homebrew tap's
`toolchains/`) is unchanged, because signing needs the `fpr-release` key, which stays with the owner. The entry to
add is [`release-indexes/fprisc-0.14.0-entry.json`](release-indexes/fprisc-0.14.0-entry.json). To offer it, from this
checkout, with the tap checkout and the `fpr-release` key on this machine:

```sh
fpr sol tools/publish-release-index.sol --tap /path/to/homebrew-tap --key /path/to/fpr-release   fprisc:0.14.0
```

The script can take several versions at once; later waiting entries are listed in
[`release-indexes/README.md`](release-indexes/README.md). After the signed index is in the tap,
`fprmeta install 0.14.0` works, and the entry file can be deleted.

## After the release: tests and targets

Checked on 15 November, after publishing, at `0a23ce2c` (the release's compiler; later commits change tests, tools and
documents only):

- **Unit test for the new passes.** `tests/InlineCalls.hs` (suite `InlineCalls`): a callee named once is merged into
  the loop that calls it, with its tail callee, and the answer, the trap and the fuel charges of 56 runs at both word
  widths are unchanged; a callee named twice and a function's own recursion are left alone; a product call is merged;
  `forward-single-valued-parameters` forwards a handle carried round a loop and ends on a cycle of unreached
  parameters (the case that made it loop for ever); dominators equal a by-definition reference on six graphs,
  including an irreducible one and unreached blocks.
- **RISC-V.** `fprc --target=rv64` of nbody and spectralnorm assembles with `riscv64-unknown-elf-gcc -march=rv64gc`;
  `fsqrt.d` and `fcvt.d.l` encode. Assembled, not executed: there is no RV64 user-mode emulator on this machine. RV32
  output is unchanged by the 15 November work (the inline float operations and the inliner are 64-bit only).
- **QOS.** QOS's sweep is now a Sol smoke check (build the host, build and pack `tests/sol-hello.fpr` as a relocatable
  app, run it). Against this compiler it passes at QOS `2fd6b1a`. At QOS `main` (`8134237`) it fails for a reason that
  is QOS's own and does not depend on the compiler: `qos/appside/hal.c` declares `fpr_wait_any_until_c` as a weak
  reference, the address test becomes a GOT relocation (`R_AARCH64_ADR_GOT_PAGE`), and `tools/qa-relocations.sol`
  refuses it. QOS's pin (`1b4aca16`) was not moved.
- **Linux x86-64.** The evidence is CI. The `sol-checks` job (the regression suite, built and run on Linux x86-64)
  passes at `031be2f9`. The `sol-native` job, which runs the compiler unit suites, had failed at its first step since
  the Benchmarks Game suite was added, because the script policy rejected that suite's Python programs; those are now
  exempt as measured subjects (`tools/sol-only-check.sol`). Nothing was timed on Linux: there is no Linux x86-64
  machine to measure on.

# Typed QOS RISC-V apps and the ESP-IDF host

Date: 2026-10-23. Kind: implementation and validation record.
Base: main `0c5b33f` (after [typed RV64 modules](2026-10-23-TYPED-RV64-MODULES.md)).
Branch `typed-ir-retire`.

Two RISC-V hosted consumers of the legacy generator were left after the
modules: a loaded QOS app or plugin (`--target=qrv64`) and the ESP-IDF host
(`--host=esp-idf`, RV32). Each differs from hosted RV64 only in where its
hart pointer lives, so each is one hart access form in `Codegen.Target.RV`
and one line of selection in `Compile.hs`.

## QOS RISC-V apps (`HartQos`)

A loaded QOS image on RISC-V has no dynamic loader to register thread-local
storage, so it borrows the host's cell through the displacement QOS
publishes at boot in `fpr_g_tlsoff` (`runtime/fpr.h`, `entry.c`): the hart
is `*(tp + fpr_g_tlsoff)`. The typed form is the legacy lowering's
(`RV64.lowerQosRV64`):

    lla t3, fpr_g_tlsoff
    ld  t3, 0(t3)
    add t3, t3, tp
    ld  t3, 0(t3)

read at every entry, after a stack-segment change and at every safepoint,
so a hart migration between safepoints is seen. There is no PIC, no TLS
relocation, and nothing else QOS-specific: RISC-V has eight argument
registers, so unlike `qx64` there are no borrowed argument cells; parameters
nine and up go through the hart's spill area as on every RISC-V target.
Plugins take the same form. QOS RISC-V apps are admitted with the QOS app
policy (fuel, the hosted ceiling), as the A64 and x86-64 apps are.

## The ESP-IDF host (`HartTlsEsp`)

The posix runtime on an ESP-IDF board keeps its hart in the thread-local
`fpr_esp_hart`, read local-exec on the 32-bit word (`runtime/fpr.h`,
`Compile.espTls`):

    lui t3, %tprel_hi(fpr_esp_hart)
    add t3, t3, tp, %tprel_add(fpr_esp_hart)
    lw  t3, %tprel_lo(fpr_esp_hart)(t3)

The RV32 policy applies: boxed floats, 31-bit Ints. The legacy text that a
unit still carries is lowered by `espTls` as before; the typed text names
the cell directly. `rvSelectionRev` 13 for both forms.

## Tests

- `tests/check_typed_ir_qrv64.py` (Base, CI's QEMU oracle stage): an
  eight-function app compiled `--target=qrv64` in strict mode: every
  function native, the borrowed form in each, no TLS relocation in the
  assembled object, no PIC, no `mv tp`; a plugin gets the same form; the
  legacy rollback keeps a separate unit identity. Execution under
  `qemu-system-riscv64`, statically linked against a C oracle whose crt
  sets `tp` to a block and whose fuel hook moves `fpr_g_tlsoff` between two
  cells holding two harts at every yield: 2,125 cases, the displacement
  moved as often as fuel ran out, both harts used, nine-argument spills
  through the borrowed hart, a string, F64, deep recursion, and the unit's
  scalar workers linked in.
- `tests/check_typed_ir_esp.py` (Base, CI's QEMU oracle stage): a
  seven-function program compiled `--system=posix --host=esp-idf
  --target=rv32` in strict mode: every function native, the local-exec
  form in each, no `fpr_posix_hart`, the rollback separate. Execution under
  `qemu-system-riscv32` against an oracle whose crt sets `tp` to the TLS
  block (`.tdata`, initialised cells): 2,105 cases, nine-argument spills,
  a string, a fuel yield on every entry.
- `tests/check_rv64_linux.py`'s lowering checks (the `qos` group:
  `fpr_g_tlsoff`, no `%tprel`, no `mv tp`, unit identities shared by the
  three qrv64 spellings) already run for both backends.

## Validation (this Mac, arm64)

- Both oracles with execution required pass: `check_typed_ir_qrv64.py`
  (2,125 cases, the displacement moved at every fuel yield, 118 yields)
  and `check_typed_ir_esp.py` (2,105 cases). The qrv64 oracle first failed
  to link because the unit emits scalar workers for its loops; the probe
  now links them too (one more thing exercised).
- `check_rv64_linux.py`'s lowering checks pass with the default backend
  and with `legacy`; `check_typed_ir_rv.py` 64 and 32, the RV64 module
  oracle, `check_profiles.py` (the ESP-IDF refusals), both retirement
  regressions, `KernelIR.hs` and `SelectedIR.hs` pass.
- `check_base.py`, every job: 110 of 110 after one test moved: the
  strict-mode "names the function that fell back" check used a `qrv64`
  compile as its refused case, which now succeeds; it uses the builtin
  profile, the one hosted-looking target the typed backend still refuses.
- CI on the push: the Linux stages, the QEMU oracle stage with both new
  checks, and the RV64 Linux typed leg.

Not verified: a loaded QOS image on RISC-V hardware or QEMU (QOS has no
RISC-V run environment in its sweep; the QOS RISC-V legs are emission
checks), and the ESP32-P4 board. Both remain acceptance gates for their
platforms; the oracles here execute the emitted code with the hart
contract substituted exactly.

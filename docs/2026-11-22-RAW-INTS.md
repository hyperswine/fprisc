# Raw Ints: versioned raw-word copies of Int loops

Date: 2026-11-22.
Kind: delivery record. Implements the raw-Int loop versioning sketched in
the [exact-Int review](2026-11-22-EXACT-INT-REVIEW.md) as the follow-up to
the v1.0 numeric slices (exact `Int` `1695e4de`, small immediates
`6d94bc23`).

## The problem

Exact `Int` lowers every `+ - * /` and ordering to `OArithVal`/`OCmpVal` on
tagged words, with a bignum slow path — so a running value is retagged at
every step, because that path may have made a bignum. A numeric loop pays
the tag/test round trip on every iteration even when every value stays
small for the whole run.

## The mechanism (`Codegen.RawInts`, pass `version-raw-ints`)

A loop's region (its header plus every block the header dominates) is
copied once. In the copy, the Int values the loop computes with are raw
`TInt` words:

- a value tagged from a raw Int is that Int;
- `+ - *` of two raw values is `OArithFits` then `OArithU`: the fit test
  branches away when the exact result leaves the small range, and
  `Codegen.Interval` removes the test where the operands' bounds prove the
  result fits (the existing no-overflow proof, which sees `TInt` again);
- any other Int the copy uses — a division's operand, a call's answer, a
  load, an operation on a value not known small — is computed as before and
  tested with `OIsInt`, then untagged;
- comparisons and equality of two raw values are `OCmp` on the words;
- a header parameter, or any value entering from outside the region, is
  tested once on the way in; failure enters the original loop instead.

A failed test leaves the copy mid-iteration. Each test point splits the
original block right after the same instruction, and the exit jumps there
with every live value retagged (the failing operation's exact result
computed on the generic path), so the original loop carries on from that
point: exact semantics, only slower. Original blocks a split reaches
without passing the header take their live values as block parameters, so
SSA dominance holds on the new edges.

**Soundness rests on one rule:** a value is raw in the copy only when it is
an Int that is small at run time. A tag of a `TInt` is small; a fit-tested
or tag-tested result is; a parameter is when every incoming edge passes a
raw value (the induction around the loop). Which `TVal` values are Ints is
inferred from their uses; a wrong guess fails a tag test and runs the
original loop — never a wrong answer.

Pipeline position: `version-raw-ints` runs in `Codegen.Simplify` after
loop-invariant motion and before `discharge-proven-checks` (the bounds
proof that drops the copies' fit tests), on W64 only, and only for
functions with exact-Int operations. A self tail call gets a new entry
block (stack check only) so the old entry can serve as a plain guarded
header; kept only when a copy is actually made. Regions are versioned
outermost-first, an inner loop copied within its outer loop's copy; a
region larger than 1200 instructions is not copied. `Simplify` gained
`OIsInt (OTag x) → True` folding and treats `OArithFits` as
cross-shareable; `Dump` prints it as `fits`.

Targets: A64 and RV lower `OArithFits` directly (A64 fuses it as a branch
condition — the exact operation then a 63-bit-fit compare, with a Mul
path that proves both operands 31-bit before falling to a divide check);
X64 selects it through the shared checked-arithmetic path. `Verify` and
the reference evaluator (`Codegen.Eval`) know the op: the evaluator still
computes the exact result and checks the fit, so a wrong proof shows as a
trap there.

## Accumulators (24 Nov 2026)

The zero-cost remeasure at `23a7a232` found std `List.fold` at `1.37x` its
hand-written loop (pairs `06`, `07`, `08a`: 40.5 vs 29.5 Ir/iter). The
monomorphised fold worker (`$typed.mono.<caller>.N`: std `foldGo` with the
callback inlined) was never copied. `versionAt`'s profitability test
(`gain`) wanted an exact operation whose two operands are both *cheap* (a
parameter or value tested once on the way in, a tag of a raw word, or
arithmetic of those). In a list walk every operation touches the element,
a cell field that is tag-tested in the copy and so never cheap: in
`a + x * k`, `x * k` has the element and `a + (x * k)` has its product. The
hand loop (`sumk`) has the same body and was not copied either on its own;
it ran raw only because `sumk` is inlined into `rep`, whose counting loop
(`k - 1`, `k == 0`) passed the test for the whole region, inner loop
included.

A loop is now also worth a copy when it has an *accumulator*: a `+ - *`
whose result reaches a raw header parameter around the loop (directly, or
through the raw parameters of join blocks in the region) and has one cheap
operand. The running value then stays a raw word from one iteration to
the next instead of being untagged, retagged and tag-tested at every step;
the element still gets its one tag test. Only the profitability test
changed: which values are raw, the fit tests, `Codegen.Interval`'s proofs
and the exits into the original loop are the same machinery, so a sum that
leaves the small range exits mid-iteration and finishes exactly (bignum,
no wrap, no trap) on the original loop.

## Branches and conversions (25 Nov 2026)

Two zero-cost pairs got worse after the exact-Int `band` of #113
(`OBitVal`) and stayed behind the hand-written loop after G11:

| pair | 23a7a232 (+#115) | 79911ce4 (#113) | c16fe82a | this change |
|---|---:|---:|---:|---:|
| 26 abstract (`both (isSmall i) (isSmall (i / 3))`) | 52.95 | 72.18 | 59.66 | 28.53 |
| 26 hand (`band i 255 < 100 and ...`) | 34.69 | 43.64 | 30.12 | 28.55 |
| 26 ratio | 1.53x | 1.65x | 1.98x | 1.00x |
| 02 F64 loop, abstract and hand | | | 33.27 | 20.23 |

(Ir per iteration, callgrind, x86-64, median of 3, `FPR_NO_RUN_CACHE=1 fpr
build`; C is 8.0 for 02.) #113 made both versions of pair 26 slower; G11's
raw `OBitVal` (901ce5c1) then helped the hand version, whose `and` reaches
the second test only on its branch, more than the abstract one.

Causes, in the copy:

- `both`'s arguments are evaluated before the call, so `i / 3`, its `band`
  and its comparison came before the first test's branch, with that
  test's predicate live across them. A test point whose live values
  include a predicate could not split its block, so the division stayed
  tagged (a runtime-call shape) and the `band` of the quotient stayed a
  tagged `OBitVal` with its tag tests.
- `F64.ofInt` of an operand that is not statically `TInt` is the runtime
  entry `fpr_prim_fn_F64_x2eofInt` (7 Ir and a call per element), even
  when the copy holds the operand as a raw word.

Changes (`Codegen.RawInts`):

- **No test, no split.** A division by a literal other than 0 and -1 of a
  raw Int is raw with no fit test (`OArithU Div`: |q| <= |x|, no zero
  divisor; the rule `Simplify.foldDivisors` already uses), and band/bor/bxor
  of two raw Ints is raw `OBit`: neither is a test point any more, so
  neither needs a split.
- **Predicates cross split edges.** A test point may split a block with a
  predicate live across it; the predicate is a block parameter of the
  split's continuation like the words are.
- **`F64.ofInt` of a raw word** is `OFloatOfInt` (one `cvtsi2sd` /
  `scvtf` / `fcvt.d.l`) where the target inlines floats; a bignum still
  runs the original loop and the runtime entry.
- **Scalar work moves into the branch that uses it** (`sinkScalars`, only
  on functions that got a copy): an instruction that cannot trap, call or
  touch memory, whose every use is under one successor of its block (that
  successor entered only from the block), moves into that successor
  before its first use. The eagerly evaluated second test of pair 26 now
  runs only on the first test's branch, as `and` does by hand.

The rest of the zero-cost suite (72 binaries, c16fe82a vs this change):
pairs 10 (`Option`) -9.1%, 18 (record return) -16.4% abstract and -11.0%
hand, every output identical; h12 (`1000000 / b` in a loop) +2.3% from a
different block layout of the same copy; everything else within 0.2%.

Compile cost (local ghc-9.8.2 x86-64, cold `fpr compile`, allocation, c16fe82a
vs this change): hello 1788008208 -> 1788521992 (+0.03%), std-live
42944416200 -> 43232656800 (+0.67%), pos1 1450779224 -> 1450630840 (-0.01%).

Gates: `test:RawInts` gains `boolpred` (pair 26's shape: the raw division
with no fit test, raw `band` of the quotient, the division under the
first test's branch, exact across the small range); `test:OptRegression`
gains `hotspots` (the same from source, and `F64.ofInt` of the raw band as
`OFloatOfInt` with the runtime entry only on the original loop);
`tests/sol-checks/raw-int-hotspots.sol` checks both shapes in the
`FPR_TYPED_IR=dump` output and prints exact answers for counters that start
as bignums. All three fail on c16fe82a.

## Limits

- W64 only (`intervalWidth` gates the pass); the 32-bit targets keep the
  tagged path.
- The copy is only taken when the region is small enough (1200
  instructions) and the loop has an entry path to guard; a loop the
  analysis cannot guard runs tagged.
- Runtime benefit requires the bounds proof (or a run that never escapes);
  a loop whose values genuinely leave the small range pays the copy's
  tests and then the original loop — slower than before by the guard
  tests, exact as ever.
- Raw-Int inference is use-based; a value guessed Int that is not fails a
  tag test into the original loop (correctness never depends on the
  guess).

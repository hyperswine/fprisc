# Research Notes: Tools, Languages, and Experiences with Linear Types, Actors, and Transactional Semantics

Compiled from academic papers, language documentation, implementations, benchmarks, and community reports. Focus on specific systems that combine two or more of: linear/substructural types (or uniqueness/capability systems derived from them), the actor model (or active objects), and transactional semantics (STM, atomic blocks, coordinated transactions, linearizability/serializability).

## 1. Linear Types / Capabilities + Actors

### Pony Language

- **What it is**: Object-oriented actor-model language (originated at Imperial College London, Sylvan Clebsch et al.). Reference capabilities on every type enforce data-race freedom at compile time. Actors communicate via asynchronous behaviors (typed messages). No shared mutable state across actors.
- **Capabilities (linear-inspired)**:
  - `iso` (isolated): Unique mutable reference (linear/uniqueness). Safe to send to another actor; ownership transfers, sender loses access.
  - `val`: Immutable, freely shareable (no copy needed).
  - `tag`: Identity only (cannot read/write); used for actor references.
  - `ref`: Mutable, local aliases only (cannot cross actor boundary).
  - `box`: Read-only alias (possible external mutation).
  - `trn` (transition): Unique writable with possible box aliases; can freeze to `val`.
- **Key guarantees**: Data-race free, memory safe (no dangling pointers, no null), deadlock-free (no locks), exception-safe. Mathematical proofs of type safety. Per-actor heaps + concurrent GC (ORCA) with no global stop-the-world pauses. Messages can pass pointers to `iso`/`val`/`tag` without copying for performance.
- **Experiences and issues**:
  - Steep learning curve: Six capabilities must be reasoned about and threaded through code (more cognitive load than Rust’s roughly two ownership modes or Erlang’s simpler model).
  - Small ecosystem and community. Pre-1.0 (regular breaking changes). Limited third-party libraries; often requires wrapping C via FFI or writing from scratch. No full IDE; debugging via GDB/LLDB with rough edges.
  - Official “Why not Pony?” page lists: lack of API stability, lack of high-quality libraries, limited tooling.
  - Positive: Used in production (claimed). High-performance niche (low-latency fintech anecdotes). Actors are cheap (~256 bytes overhead). Flat latencies under consistent load due to per-actor GC.
  - Origin story: Motivated by data-race bugs in high-performance C actor libraries at a bank; library approach insufficient, so language+runtime designed together.
- **Performance notes**: Lock-free by design. Native AOT compilation. Suitable for high-throughput concurrent systems. One podcast anecdote of a matching engine handling 10M orders/sec with sub-ms latency (not independently verified in primary sources here).
- **Related paper**: “Deny Capabilities for Safe, Fast Actors” (2015/2016).

### Encore Language (and Kappa Capabilities)

- **What it is**: Research language (Uppsala University / UPSCALE project) with active objects (actors), capability type system (Kappa) for data-race freedom, futures. Distinguishes active (actors) and passive objects. Capabilities attached to objects (vs. Pony’s references).
- **Extensions for isolation/atomicity**:
  - **Bestow**: Allows an actor to share a reference to an internal passive object. External calls are delegated to the owning actor (asynchronous message under the hood). Decouples interface from ownership. Can be combined with linear types for ownership transfer.
  - **Atomic** blocks: Group multiple messages/operations on an actor (or bestowed object) so they execute without interleaving from other senders. Provides higher-level atomicity. Implemented via private mailboxes or batched closures. Borrowed handle that cannot escape the block.
- **Experiences and issues**:
  - Bestow overhead: In a ping-pong benchmark, bestowed version was 11–16× slower than pure actor version (constant factor).
  - Atomic can reduce overhead or improve performance in cases with many small operations (break-even depending on message count); enables reacting to intermediate results and finer-grained interfaces.
  - Implementation challenges: Tracing/GC for bestowed objects, race conditions in atomic mailbox scheduling. Prototypical implementation being hardened.
  - Case studies: Distributed hash tables/arrays, graphs, atomic money transfer. Locally distributed data structures backed by multiple actors for parallel disjoint operations.
- **Related papers**: “Bestow and Atomic: Concurrent Programming using Isolation, Delegation and Grouping” (2018); theses on implementing safe sharing in Encore.

### Session Types, Mailbox Types, and Behavioural Types for Actors

- Linear and session types from process calculi adapted to actors.
- Challenges: Actor mailboxes are many-sender/single-receiver; pure linear types insufficient (need multiple sends). Solutions use quasi-linearity, mailbox types (characterizing accepted messages), behavioural types for protocols.
- Examples: Work on typed actors (λact calculus translating to/from channels), mailbox types with backwards bidirectional typing, typestate-like process types for actor handles (tokens consumed on receive, obligations for sends).
- Issues: Dynamic sets of actors harder than fixed-session participants; selective receive and asynchrony complicate translations. Pure linear assumptions can lead to overly restrictive or incomplete matching of sends/receives.
- Related: Rast (verified linear session-typed concurrent programming); Links language extensions; papers on actor capabilities for message ordering, mixing metaphors (actors as channels and vice versa).

## 2. Actors + Transactional Semantics

### Chocola (Composable Concurrency Language)

- **What it is**: Extension of Clojure providing futures (deterministic parallelism), actors (message passing), and transactions (STM shared memory). Designed so the three models can be freely mixed while preserving individual guarantees.
- **Problems with naive combinations**:
  - Sending messages or spawning inside a transaction can break isolation (effects visible even on abort; messages sent multiple times on retry).
  - Shared memory between actors breaks actor isolation and can reintroduce races/deadlocks.
  - Futures inside transactions or vice versa can break serializability or determinism.
- **Solutions / guarantees**:
  - Transactional actors: Shared memory protected by transactions; actor-internal memory remains isolated. Consistent turn principle (variant of isolated turn).
  - Transactional futures: Parallelism inside transactions while preserving serializability/snapshot isolation.
  - Overall: Serializability (or snapshot isolation), freedom from low-level data races and deadlocks, message-passing integrity where applicable. Formal operational semantics (PureChocola) with proofs.
- **Implementation**: Clojure library (patches at startup). PLT Redex executable semantics available. Open source (Eclipse Public License).
- **Experiences and performance** (STAMP benchmarks modified: Vacation2, Labyrinth, Bayes):
  - Can improve performance with relatively little developer effort by exploiting more parallelism (parallel transactions via futures, or actor-based distribution of work with transactional shared state).
  - Specific numbers (from paper excerpts): Max speed-up of 11.0 (Vacation2 with 38 primary + 8 secondary workers). Overhead of transactional actors: ~2× slower than pure on single worker (5,656 ms → 14,377 ms). Labyrinth parallel search improvements with more partitions. Bayes up to ~3.33× with mixed workers.
  - Limitations noted in repo: Actor GC (unreachable actors stay forever), exception interaction needs more testing, commute not fully working with transactional futures, performance TODOs.
  - Follow-up energy study (preprint): Chocola variants showed better time and energy performance than baseline transactional models in some configs (e.g., CHO-2 median ~2.66s / 138.7J); positive correlation between performance and energy savings in some cases (unlike standard models).
- **Related papers**: TOPLAS 2021 (full paper); AGERE 2018; earlier SEPS 2017 (Transactional Actors) and ECOOP 2016 (Transactional Tasks/Futures).

### Akka Transactors

- **What it is** (historical, Akka ~2.2): Combines actors with STM (Multiverse). Allows coordinated transactions across multiple actors via `Coordinated` objects and CommitBarrier (like CountDownLatch). Actors can update transactional Refs atomically; messages can carry coordination.
- **Use cases**: When pure actors are insufficient for consensus/shared view of state (e.g., bank transfer across accounts). STM rarely needed otherwise.
- **Issues and outcome**:
  - Explicit coordination; risk of deadlock if same actor added twice to one coordinated transaction (processes one message at a time).
  - Deprecated in Akka 2.3: “Transactors won’t make much sense in a clustered environment.” Conflicts with Akka’s location transparency goal. STM support for agents also deprecated.
  - Broader Akka actor experience (separate study of 186 real bugs from SO/GitHub): Common symptoms include errors, unexpected behavior, incorrect messaging. Root causes: logic errors most common (~19%), then races, API confusion, lifecycle, messaging patterns, model confusion. Untyped communication less common. Small number of API packages dominate bug-related usages.
- **Related**: “Transactors: Unifying Transactions and Actors” (Lesani, Odersky, Guerraoui, 2009) — earlier formalization addressing composability and deadlock with cyclic communication.

## 3. Linear Types + Transactional Semantics

- **Move language** (blockchain/smart contracts, Sui etc.): Linear types for resources (coins, assets). Compiler prevents accidental loss, duplication, or use-after-move. Provides resource safety in a transactional execution model (atomic transactions on-chain). Formalized subsets prove resource preservation.
- **Haskell**: Mature STM (TVars, atomically, retry, orElse; snapshot isolation / opacity). Linear types (GHC 9.0+, experimental `-XLinearTypes`, multiplicity polymorphism) primarily for resource management, safe mutation, fusion predictability, and protocols — not core to STM. Can be combined for stronger resource guarantees inside transactional or concurrent code. Linear promises proposed for safer concurrent ownership of fulfillment.
- **C4: Verified Transactional Objects** (OOPSLA 2022): Framework for verifying objects that mix classical concurrent objects (linearizability) and STM-style transactions (serializability). Mechanized in Coq; case study of transactional set via transactional predication. Compositional reasoning via interaction trees.
- **Relaxed linearity / ownership for concurrent structures**: Work on types for CAS-based lock-free algorithms (ownership treated linearly while allowing non-owning aliases). Useful for STM-like or concurrent data structures.

## 4. Common Issues, Experiences, and Observations Across Systems

- **Naive mixing breaks guarantees**: Actors + STM/transactions often lose isolation (messages or side effects escape aborts) or reintroduce races/deadlocks. Futures + transactions can lose determinism or serializability. Capability/linear systems solve races statically but add annotation burden and restrict sharing patterns.
- **Performance trade-offs**: Capability-based zero-copy sharing (Pony) or delegated sharing (Encore bestow) can be fast when used carefully but have overheads (bestow 11–16× in microbenchmarks). Transactional actors have noticeable constant-factor overhead but enable higher scalability via better parallelism. STM in general suffers under high contention (retries).
- **Usability and adoption**:
  - Capability systems (Pony, Encore/Kappa) have steep learning curves; users must internalize denial rules and aliasing modes.
  - Small ecosystems for pure research languages (Pony pre-1.0, Encore research, Chocola research library).
  - Production actor systems (Akka, Erlang/Elixir) often prefer pure isolation or explicit coordination over full STM integration; location transparency and distribution complicate shared transactional state.
  - Actor bugs often stem from logic, lifecycle, and messaging patterns rather than classic data races (when isolation is enforced).
- **Verification and formal work**: Many systems have formal semantics, progress/preservation proofs, or mechanized verification (Coq, Redex). Linearizability checking tools for actor systems exist (e.g., DS2).
- **Related practical systems**: Rust (affine types + channels or actor frameworks like Actix); Erlang/Elixir (actors, no linear types natively); Clojure (STM + agents/atoms, basis for Chocola); Scala/Akka (actors, historical STM).

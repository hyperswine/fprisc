# Exokernels, microkernels, and capability-bounded memory

Research notes for FP-RISC and QOS · 12 November 2026

The closest hardware precedent is CHERIoT. Compartments occupy one physical address space, pointers carry bounds and permissions, and a common heap allocator charges allocations against explicit capabilities. The closest software precedent is RedLeaf. It put applications, drivers, and OS services in language-isolated domains, transferred ownership of shared buffers, and measured the cost of adding transparent driver recovery. Genode is the closest precedent for the file interface. The same filesystem plugin can run in an application or in a filesystem server, and a client can fund the memory that a service consumes on its behalf. Each demonstrates a different part of the proposed architecture. CHERIoT RTOS · RedLeaf · Genode VFS · Genode resource trading

## 1. OS policy as application library code

MIT exokernels — pay for authorization when establishing the binding

Aegis separated resource protection from management policy. A library OS could decide how to use a resource, while the kernel established a secure binding between the application and that resource. The relatively expensive decision about authority could happen at bind time. Subsequent uses still had to respect the binding, enforced through mechanisms such as hardware translation or a kernel-installed packet filter. A physical address or a packet matching a filter only remained usable under the corresponding binding. The kernel could request a resource back, let the library choose what to release, and forcibly reclaim it when cooperation failed. This is a direct precedent for bind-time authorization and also a reason to specify revocation as part of the interface. Aegis itself used virtual-memory hardware. Engler, Kaashoek & O’Toole, SOSP 1995

The later Xok/ExOS evaluation distinguished two questions often collapsed into one. Compatibility: ordinary Unix applications in their suite generally performed comparably to or better than the BSD systems tested. Specialization: the Cheetah web server exploited access to the file cache and network path. For documents of 1 KiB or less, the specialized path achieved roughly 4× the throughput of the conventional-interface version on Xok and 8× the best OpenBSD result the team obtained. The within-Xok comparison matters because it holds more of the system constant. These were 1990s systems and workloads. The result establishes that removing an abstraction boundary can enable a specific optimization. Xok/ExOS application study · Cheetah baselines, §5 and Figure 5-2

Two nearby designs clarify what “same space” can mean. MirageOS links a selected OCaml network and OS stack with an application into one specialized image. This demonstrates how much of an OS can be ordinary library code; the image alone supplies no independent restart contract for each linked library. Nemesis moved common processing into the client domain and kept shared-resource arbitration in a server. It gave domains a common virtual address map with different page permissions, and implemented inter-domain communication using shared buffers and event counts. A common pointer value there did not confer a right to dereference it. MirageOS · Nemesis design · Nemesis IDC

## 2. One address space with protected components

CHERIoT — the shared allocator the proposal describes

CHERIoT targets embedded systems with a single physical address space and no conventional MMU requirement. Hardware capabilities carry bounds and permissions. A caller can pass a bounded buffer to a compartment while keeping the rest of its storage inaccessible. The RTOS distinguishes a library call, which executes with the caller’s authority and supports code and read-only data, from a compartment call, which enters a separately protected component with its own private globals. That gives a concrete placement rule: a parser that only transforms a supplied buffer can be a library; an allocator that owns mutable global metadata can be a compartment. MMU-less systems classification · CHERIoT guide, compartments and libraries

The allocator exposes two distinct kinds of capability. Its allocation capability authorizes spending a quota and freeing the resulting allocation. The pointer capability returned to the caller authorizes access to the allocated bytes. Giving a driver a buffer therefore need not give it permission to free that buffer or charge further allocations to the owner. Padding and allocator metadata count against quota. Allocation can still fail or wait when the shared heap cannot satisfy a request. A quota is a ceiling; reserving enough usable space for a request requires a separate argument about competing users and allocator layout. Programmers’ guide, memory management and allocation API

The cost of safe reuse depends on workload. In the authors’ experiment with 128 KiB allocations, each allocation required a revocation sweep over almost 256 KiB of SRAM. Scanning dominated the allocation cost; a hardware revoker helped. At small sizes the compartment crossings into the allocator mattered more. These observations identify two different benchmark cases for a global allocator: many tiny allocations and repeated reuse of a large fraction of the heap. CHERIoT evaluation, Table 4 and discussion

RedLeaf and CheriOS — two ways to colocate a driver and its clients

RedLeaf used safe Rust domains in one address space. Each domain had private storage. A separately managed shared heap held objects whose ownership could cross domains through an RRef<T>. A trusted proxy checked whether the callee was alive, recorded enough state to unwind a failed call, and transferred ownership of arguments. This was a synchronous protected call. Building an actor mailbox on that substrate would add queuing and scheduling costs. The design trusted its compilation environment, low-level unsafe crates and non-malicious devices, including the device DMA path. RedLeaf paper, §§3–4

The authors measured 124 cycles of overhead for an empty cross-domain invocation through a proxy, 17 additional cycles to pass one shared reference, and 286 cycles for the invocation through a recovery shadow and two proxies. The 286 cycles describe a successful call through the recovery machinery; they do not measure the time to restart a driver. In end-to-end tests, their 10 Gb/s Ethernet and NVMe drivers matched the DPDK and SPDK counterparts tested. The paper also reports recovery of driver domains. This is evidence that an independently recoverable component can be competitive on the normal path. RedLeaf, Table 1 · Authors’ results

CheriOS provides a worked deployment with a different split. In its NGINX experiment the filesystem, block cache, block driver, network stack and web server ran as separate compartments. The Ethernet driver was linked with the network stack while retaining its own compartment. Processes used event loops and control messages, and used CheriOS sockets for bulk data. The nanokernel, microkernel and socket library were callable as dynamic libraries. CheriOS used a single virtual address space and retained page-table management. CHERIoT supplies the closer precedent for eliminating paging; CheriOS supplies the richer example of arranging linked code, distinct authority, and IPC in one application. CheriOS thesis, chapters 5–6

What a conventional microkernel buys

L4Linux ran Linux as a server on L4. In the 1997 AIM multiuser benchmark, maximum throughput was 5% below native Linux on the tested system. That provides a useful counterpoint to the shared-space results: a hardware-protected server boundary can also be affordable. seL4 illustrates another division of responsibility. At startup, the root task receives capabilities to available untyped physical memory and can split or retype it into frames and kernel objects. Microkit declares protection domains, memory regions and communication channels in a system description. This supports budgeting physical resources up front. The seL4 kernel proofs cover specified configurations and assumptions; an application still needs a separate proof that its algorithm fits its assigned budget. L4Linux evaluation · seL4 untyped memory · Microkit manual · Proof scope

## 3. Restarting a service while its clients keep running

|System |What happens at the boundary                                                                                                                                                        |What the client or supervisor must know                                                                                                                                                                                                                               |
|-------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|RedLeaf|A proxy can unwind a failed invocation. A shadow domain can keep a stable interface and replace a driver behind it.                                                                 |Recovery code needs a way to reconstruct usable driver and device state. [RedLeaf](https://pdos.csail.mit.edu/6.828/2024/readings/redleaf.pdf)                                                                                                                        |
|Hubris |A supervisor can reinitialize a statically allocated task. Its task index persists and its generation changes. A send or closed receive using a stale generation reports peer death.|The caller decides whether to retry or run an initialization handshake. A generation identifies a service incarnation; it carries no record of which writes completed. [Hubris IPC, “Death and IPC”](https://github.com/oxidecomputer/hubris/blob/master/doc/ipc.adoc)|
|MINIX 3|The reincarnation server starts a replacement driver and publishes the new endpoint. Other services update their bindings.                                                          |Recovery depends on the upper-layer protocol and the device’s ability to reset. TCP can recover missing packets while its state survives above the failed driver. [Driver recovery study](https://www.minix3.org/docs/jorrit-herder/dsn-dccs07.pdf)                   |

MINIX 3 measured the interrupted workload. Researchers downloaded a 512 MB file over TCP while killing the Ethernet driver every 1–15 seconds. Every transfer completed and its checksum matched. Throughput went from 10.8 MB/s uninterrupted to 8.1–10.7 MB/s under repeated failure. Mean recovery time was 0.48 s, partly due to TCP retransmission. A separate emulator experiment recovered from all 347 detectable crashes. In preliminary real-hardware tests, a few faults left the network card in a state that required a BIOS reset. The distinction matters for a restart guarantee: fresh software state is within the OS’s control; recovering an external device depends on what reset operations the hardware exposes. MINIX 3, §§7.1–7.2

For a QOS file service, consider a crash after a driver appends a record but before the client receives the reply. A new endpoint lets the client reconnect. A new generation lets it discard stale handles. Neither tells it whether another append would duplicate the record. A proposed interface could expose an unknown outcome, make the write idempotent by specifying a fixed location and content under suitable concurrency rules, or support a durable operation ID whose outcome can be queried. The choice belongs to the operation’s contract. A read-only status file and an append-only log can justify different recovery policies.

## 4. Four meanings of a memory bound

|Claim                                                          |Concrete implementation or evidence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
|---------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|**An access cannot touch bytes outside the authorized region.**|CHERIoT checks pointer bounds and permissions. WebAssembly bounds a load or store against the current linear memory and traps an out-of-bounds access. A Wasm linear memory can still contain many application objects; its outer boundary provides no per-object separation within that memory. [CHERIoT](https://cheriot.org/book/cheriot-programmers-guide.pdf) · [Wasm specification](https://www.w3.org/TR/2026/CRD-wasm-core-2-20261009/)                                                                      |
|**A component cannot claim more than a configured amount.**    |A CHERIoT allocation capability limits what its holder can charge. Wasm `memory.grow` fails if growth would exceed the declared maximum and can also fail for lack of resources. A Wasm page is a unit of linear-memory size; the abstract machine does not require hardware page tables. [Allocator API](https://cheriot.org/book/cheriot-programmers-guide.pdf) · [Wasm specification](https://webassembly.github.io/spec/core/_download/WebAssembly.pdf)                                                          |
|**Capacity has already been assigned to a task.**              |Hubris fixes tasks and resource allocation at build time and isolates tasks on microcontrollers. An overflowing stack can still fault. Tock likewise uses an MPU for processes and safe Rust for kernel extensions; its grant mechanism lets the kernel reclaim a dead process’s associated service state. [Hubris](https://hubris.oxide.computer/) · [Hubris fault example](https://github.com/oxidecomputer/humility/blob/master/README.md) · [Tock, SOSP 2017](https://tockos.org/assets/papers/tock-sosp2017.pdf)|
|**Every execution within the stated assumptions fits.**        |CakeML’s verified space-cost semantics relates heap and stack reasoning to compiled machine code, including GC. For the paper’s x64 `yes` program, **56 machine words of stack and 89 words of heap** suffice under its machine and FFI assumptions. The program can emit output indefinitely while keeping live storage bounded. These figures cover the specified stack and heap, excluding code and external I/O infrastructure. [CakeML proof, §6 and the `yes` theorem](https://cakeml.org/oopsla20.pdf)        |

For automatic inference, Resource Aware ML derives input-size-dependent upper bounds for supported OCaml programs by solving resource constraints. Its documented metrics include allocated heap cells and evaluation steps. That gives a plausible path for inferring a bound for a pure decoder over a bounded packet. Converting that result into a whole-service RAM bound requires a representation cost, a stack bound, and accounting for concurrent or queued work. Total allocation over time and maximum live memory can differ dramatically in a long-running actor. RaML analysis and limits · CakeML live-space semantics

## 5. Plan 9 naming with explicit authority

Plan 9 supplies naming and protocol composition. A process can use bind and mount to assemble its own namespace. A server exports a file tree; ordinary file operations become 9P requests. An attachment establishes a root fid, walk derives another fid along a path, and clunk releases a fid. The server interprets these identifiers within the connection and attachment context. A fid number copied into another client’s message is therefore insufficient as a general transferable capability. Plan 9 namespace bind changes what a name resolves to; exokernel secure binding establishes authority over a resource. The two operations can be combined in a design while retaining distinct semantics. Plan 9 from Bell Labs · 9P walk semantics

Genode demonstrates the placement choice. Filesystem plugins are shared libraries. A program can use the VFS library directly, or a VFS server can host the plugin and export its service to clients. Existing plugins expose network packets, tracing, and pipes through file interfaces. Genode also addresses indirect resource consumption: a client can donate part of its RAM quota when opening a session, funding state held by the server. Closing the session returns that quota. This matters if, for example, a nominally bounded application can otherwise create arbitrarily many directory cursors or pending reads in someone else’s heap. VFS components · Session resource trading

WASI and Capsicum supply concrete authority rules. WASI filesystem operations resolve paths relative to a directory descriptor. Resolution that escapes the starting directory, including through .. or symlinks, fails. Capsicum restricts access to global namespaces in capability mode and lets programs operate through rights-limited descriptors. Together with Plan 9, these suggest a small interface in which a component receives an authorized directory, walks a relative name, and obtains a narrower handle. An application can still display a familiar path such as /dev/net/status; its ability to resolve that path derives from the roots it received. WASI filesystem interface · Capsicum

## 6. A concrete QOS experiment

The following is a proposed experiment, separate from the published results. Implement one file service with a bounded request queue and run the same workload through three placements: a library call in the client, a synchronous call across a protected component boundary, and a request/reply exchange with an independently scheduled service. Holding the payload representation and file semantics constant makes the cost of placement visible.

|Stage   |What to measure or establish                                                                                                                                                                                                                                                                                |
|--------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|Bind    |Give the client a directory capability, resolve one child, and issue a handle with specific rights. Measure first lookup separately from repeated reads. Define what happens to an existing handle after revocation.                                                                                        |
|Transfer|Sweep payload size from a few bytes to a full buffer. Compare copying with handing over a bounded buffer. Record identity checks, ownership changes, queue occupancy, and elapsed time separately.                                                                                                          |
|Account |State an admission limit and charge each admitted request for its payload, descriptor, pending reply, and server-side metadata. Include fixed stacks, allocator overhead, and any old buffers retained across restart. Test exhaustion behavior as well as ordinary use.                                    |
|Recover |Restart before acceptance, after acceptance, after an external effect, and after reply delivery. Record what each party knows, which allocations can be reclaimed, and whether retry preserves the operation’s meaning.                                                                                     |
|Verify  |Prove the memory requirement of one handler for bounded input, then combine it with the maximum simultaneous requests and the service’s fixed costs. Measure peak RAM independently as a check on the model. A measured peak is evidence about the test cases; the proof must cover all admitted executions.|

Research conclusion. There are working precedents for bind-time authorization, OS policy in libraries, protected same-space calls, an MMU-less shared capability heap, generation-aware restart, and file-relative authority. The performance studies make those mechanisms credible individually. The open engineering question is their composition: who pays for a buffer while a request is queued, who may reclaim it when a service dies, and what can the client safely do after rebinding? A single file operation exercised across those transitions would test more of the proposed architecture than an isolated IPC latency number.

# Linear types, actors, and transactions in practice

Three questions arise when an actor hands another actor a buffer and asks it to write a file. Who can still use the buffer? When can other actors observe the write? What does the caller know if the reply never arrives? Eight implementations provide different pieces of the answer. Their evidence ranges from OS microbenchmarks and a controlled programmer study to runtime bug reports and documented language semantics.

## Moving data and accounting for ownership

### Singularity and Sing# — transferring a packet buffer between processes

Microsoft’s Singularity OS used channels with contracts that specified the legal sequence of messages. A message could transfer ownership of a memory block or a channel endpoint. In the network stack, a component could strip a packet header by changing the bounds of a view into a buffer. The next component could then receive the payload without copying its bytes. After eight months, the OS had **43 channel contracts, roughly 500 distinct messages, and 135 protocol states**. The team reported that initially skeptical developers came to value contracts for catching mistakes and understanding how components interacted. [Channel implementation and experience, §6](https://www.microsoft.com/en-us/research/wp-content/uploads/2006/04/singsharp.pdf) · [Exchange heap design, §3.3.2](https://www.microsoft.com/en-us/research/wp-content/uploads/2005/10/tr-2005-135.pdf)

Two measurements from the 2006 prototype distinguish payload cost from handoff cost. Sending and receiving a memory block cost about **1,200 cycles across sizes from 1 byte to 64 KiB**. In a separate one-byte ping-pong benchmark, a round trip between processes cost about **15% more** than ping-pong between threads in one process using a wait set. Increasing the payload barely affected the first measurement. The second still captured the fixed cost of a handoff. [Benchmarks, Table 1 and Figure 5](https://www.microsoft.com/en-us/research/wp-content/uploads/2006/04/singsharp.pdf)

### Pony — an immutable message can keep an actor alive

Pony’s ORCA collector coordinates reference accounting through actor messages. A tracing optimization skipped traversing a graph sent under an immutable root. In 2022, maintainers described a failure where that graph contained an actor reference. The runtime could reclaim the referenced actor while the recipient could still reach it. The immutable root told the collector that the graph could never change. Reclamation also depended on which actors the graph kept alive. [ORCA design](https://www.doc.ic.ac.uk/~scd/icooolps15_GC.pdf) · [Maintainer’s account of the bug and fix](https://www.ponylang.io/blog/2022/12/last-week-in-pony---december-11-2022/)

Tracing every object sent between actors fixed the accounting issue. A maintainer observed a **roughly one-third performance drop** in informal testing with a modified message microbenchmark and considered it likely near the high end. The proposed refinement was to have the compiler identify types that might contain actor references and let the runtime skip tracing when it could prove their absence. [Measurement and proposed refinement](https://www.ponylang.io/blog/2022/12/last-week-in-pony---december-11-2022/)

### Obsidian — how programmers handled assets under a linear type system

A study assigned ten programmers each to Obsidian and Solidity. Obsidian treats assets as owned resources and tracks which operations are legal in a particular contract state. The auction and casino exercises exposed different consequences of those rules. [Study design and results](https://www.cs.cmu.edu/~jssunshi/assets/pdf/usableAdvanceTypeSystems.pdf)

| Task | Observed outcome |
| --- | --- |
| Auction | Of the nine Solidity participants who believed they had finished, seven introduced an asset-loss bug. None of the eight Obsidian participants who believed they had finished lost assets. |
| Casino | All four Obsidian participants who finished improperly used `disown` to discard assets. One discarded the previous wager and paid winnings from the casino’s own pot. |

The authors pointed out that removing `disown` would still leave a programmer free to transfer unwanted tokens into an object that holds them forever. The compiler can account for each transfer while the application sends money to the wrong destination. The small sample supports a task-specific observation: the same programmers’ tools can prevent accidental loss in one exercise and admit a deliberate workaround in another. [Auction summary](https://obsidian-lang.com/experiment.html) · [Casino observations and participant examples](https://www.cs.cmu.edu/~jssunshi/assets/pdf/usableAdvanceTypeSystems.pdf)

### Linear Haskell — consuming a serialized tree through a cursor

Researchers implemented two operations over packed binary trees: sum the leaves and increment each leaf. A linear cursor tracked the remaining input as each field was consumed. Processing large trees directly in their serialized representation produced **over 20× speedup** against unpacking, transforming, and repacking. The speedup came from avoiding the representation change. Linearity let the authors expose a safe interface to that implementation. They also implemented packed traversal with the `ST` monad. Their linear version used unboxed results to eliminate intermediate allocation that remained in their `ST` implementation. [Linear Haskell, §5.1 and Figure 7](https://assert-false.science/arnaud/papers/Linear%20Haskell%20practical%20linearity%20in%20a%20higher-order%20polymorphic%20language.pdf)

## What commits, and what can still fail?

### Haskell STM — a speculative computation can interfere with progress

Haskell lets small `STM` actions compose inside a single `atomically` block. For example, removing a job from one transactional queue and adding it to another can commit as one operation. If the source queue is empty, `retry` lets the transaction wait for a relevant change. An action can also use `orElse` to try another queue when the first would block. [Composable Memory Transactions](https://timharris.uk/papers/2005-ppopp-composable.pdf)

A 2015 study on a **72-hardware-thread Haswell system** exposed a failure before commit. A transaction could read temporarily inconsistent data and enter a non-allocating infinite loop. Allocation was where the runtime normally checked whether a thread needed to stop for garbage collection. The thread could therefore hold up GC indefinitely. A straightforward fix cost **roughly 5%** in the researchers’ experiments. In a separate comparison, updates to a persistent data structure behind one mutable root performed well through about eight cores in their workload. Beyond that point, contention on the root favored finer-grained STM. [An Update on Haskell H/STM](https://www.cs.rochester.edu/u/scott/papers/2015_Yates_TRANASCT_GHC_HTM.pdf)

### Motoko — an ordinary await commits the work before it

A Motoko actor can update its state, send a request, and suspend at `await`. At that boundary the preceding state changes and message sends become irrevocable, even if the awaited future is already complete. Another message can run before the continuation resumes. For example, if an actor records `DebitPending`, awaits a reply, and then records `Settled`, other handlers can observe `DebitPending`. A trap in the continuation can leave the debit in that state. This makes a pending state part of the actor’s observable protocol. [Motoko language reference, await expressions](https://docs.internetcomputer.org/languages/motoko/reference/language-manual/)

### Orleans — allowing a transaction to span actors

Orleans supports distributed ACID transactions across the persistent state of multiple actors, called grains. One implementation released locks during the first phase of two-phase commit so later transactions could proceed while earlier ones waited on storage. It tracked dependencies so that an earlier abort could also abort transactions that depended on it. The authors measured **up to 20× the throughput** of their conventional two-phase-locking and two-phase-commit baseline. A later paper describes prefetching actors’ state before acquiring locks, which usually avoided holding locks while waiting for cloud storage reads. [Distributed transaction protocol and benchmark](https://www.microsoft.com/en-us/research/publication/transactions-distributed-actors-cloud-2/) · [Later Orleans implementation](https://www.microsoft.com/en-us/research/publication/cloud-actor-oriented-database-transactions-in-orleans/)

### FoundationDB — a commit and its acknowledgement are separate events

FoundationDB documents an atomic increment that can be applied twice. The first transaction commits, but the caller receives `commit_unknown_result`. If the caller runs the increment again, the second transaction can also commit. The documented automatic idempotency option addresses this error, while some other errors still leave commit status unknown. FoundationDB also runs database code in a deterministic simulator, where developers can inject cluster failures and replay a failing execution from its seed. [Increment example and idempotency semantics](https://apple.github.io/foundationdb/automatic-idempotency.html) · [Simulation and testing](https://apple.github.io/foundationdb/testing.html)

## Applying the cases to FP-RISC and QOS

Consider a file service that takes ownership of a buffer and replies when a write completes. A caller that has reached `FileWriteReqSent` may eventually receive `FileWriteRes`, time out, or restart. The research suggests four separate questions for that interface.

| Design question | What the case contributes |
| --- | --- |
| Who can access the buffer after the request is accepted? | Singularity gives ownership transfer an explicit point in the message protocol. Pony shows why the runtime must also account for references reachable through a transferred value. |
| Which intermediate states can other handlers observe? | Motoko makes suspension a commit boundary. Orleans supports a transaction across participants and incurs the coordination and recovery work that requires. |
| What does a missing reply authorize the caller to do? | FoundationDB gives an unknown outcome its own representation. Retrying a write that appends data or advances a cursor can have a second effect even when each individual write is atomic. |
| Can an operation that will never commit still delay other work? | The Haskell STM experiment shows how a speculative loop can obstruct GC. This is a concrete test case for a runtime that relies on fuel checks or safe points for progress. |

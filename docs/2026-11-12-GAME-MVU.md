# A pure MVU interface for FP-RISC games

Proposal, 12 November 2026. The baseline is FP-RISC 5c24b339. The first consumers are Dungeon a17c941 and Terra II 5253bb2. The signatures below describe a proposed API.

## What a game author writes

```text
init   : Flags -> (Model, Cmd Msg)
update : Msg -> Model -> (Model, Cmd Msg)
subs   : Model -> List (Sub Msg)
view   : Model -> Element Msg

main = Game.run config (Game.app init update subs view)
```

The game defines its own Model and Msg. Update dispatches each message to a small pure handler. Rules, key bindings, save codecs and scene builders can live in separate modules. Flags are immutable startup data, such as a supplied seed. Window size and asset declarations belong in config. Actor IDs, open files, sockets, render contexts and driver configuration belong to the backend.

For example, a key subscription decodes a key into an optional Move North message. Update applies movement and returns the new model plus a sound command if the move opened a door. View builds the door in its new position. A second call to view can rebuild the identical tree without replaying the sound.

## Library contract

| Abstraction | Responsibility |
|---|---|
| Msg | The only input to update. Keys, ticks, pointer gestures, resize, network events and task results enter the same serialized update loop. Decoders turn library events into game vocabulary and may ignore an event. |
| Sub Msg | A pure description of continuing interest, such as a keyboard decoder or a periodic tick. Reconcile subscriptions by stable identity after each transition. An unchanged timer keeps its cadence. Removing a subscription releases its registration. |
| Cmd Msg | A pure description of one-shot work. Provide an empty command, ordered commands, sound, logging, frame capture and quit. Interpret each emitted command once per accepted transition. Rendering or re-evaluating a pure function cannot dispatch it. |
| Task error value | A description of fallible work, such as loading a save, writing a record, or fetching network data. An attempt operation maps its Result to a game Msg. The backend dispatches the completion later. Independent tasks may finish out of order. Sequence dependent work explicitly and include request IDs when stale results matter. |
| Element Msg | An immutable tree describing the world scene, camera, overlays, HUD and any input bindings. The game owns composition and visual design. The renderer owns traversal, draw order within declared layers, GPU resources and presentation. Capture targets the frame for the requesting transition after it has rendered. |

Commands describe intent. Durable delivery and safe retry depend on the storage or network protocol. A completed append with a lost reply must be distinguishable from a request known to have failed before publication if the app offers retry. On shutdown the runner owns subscription teardown, task cleanup and device release. Games needing confirmation before quitting can model that choice in update.

## Delivery and acceptance

1. Build a small game-facing façade over the existing frame loop. FP-RISC owns the application vocabulary and pure contracts. The QOS adapter opens services and interprets effects. Existing std/mvu already provides input events, subscriptions, a frame loop, logging and quit commands. Its current game driver accepts an environment and permits service reads during rendering. Keep those details behind the new runner. [Current driver](../std/mvu.fpr)
2. Provide a headless interpreter that accepts scripted messages, records commands, and lets tests supply task results. Verify deterministic model and element output, one sound across repeated renders, timer removal, and correlated task failure. Check the application boundary with a negative fixture, for example a direct print or Files request inside view must fail the chosen purity check. Until that check exists, describe purity as a convention.
3. Migrate Dungeon to exercise the minimal surface, then Terra II to exercise sound, ordered storage and failure recovery. Retain each game's graphical smoke test. Ship the façade and QOS adapter together in a staged SDK and build each standalone game using that SDK. Network tasks follow the same contract when a game needs them.

Game-specific plans live in the Dungeon and Terra II repositories under docs/2026-11-12-GAME-MVU.md.

## Replaceable computation tasks

Proposed Cmd constructor: Task.latest key revision job onResult. A game submits an immutable input to a named computation. The runner may keep a worker actor alive for that key. Each key has at most one active search and one pending input. A new submission replaces the pending input. The worker checks for replacement after each bounded chunk, discards superseded search state and starts the newest input. A pure job supplies start and step functions; step advances a fixed work budget and returns More state or Done result. Explicit cancellation releases both active and pending state at a chunk boundary.

The result arrives as a Msg carrying the key and revision. Update accepts it only for the outstanding request in the current game session. This covers a completion already queued when a restart or replacement occurs. Revisions advance on changes to search inputs, not every animation tick. Use latest semantics for disposable computations. Ordered saves and other externally visible writes need their own acknowledgement semantics.

A headless driver can step jobs deterministically. Submit A, replace it with B then C within one chunk, and verify C completes, B never starts and a queued A result cannot change the model. A responsiveness check records the longest chunk and input-to-frame delay during search. Cooperative concurrency works on one execution context; parallel execution requires an independently scheduled worker and available processing capacity.

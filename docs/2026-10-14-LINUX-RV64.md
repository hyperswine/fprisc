# Linux riscv64 support

Kind: implementation and hardware validation. Added 2026-10-14 against
FP-RISC `0f4f6c2` plus this working-tree change (codegen revision 41).

Linux riscv64 uses the existing `posix` system and Unix host. It is not a
separate language profile or runtime adapter. The supported ABI is RV64GC,
LP64D, with libc and pthreads. There is no RVV requirement. The STAR64's
SiFive U74 cores execute this baseline directly.

## Build

On a riscv64 Linux machine with a built compiler and C toolchain:

```sh
./fpr build tests/base/hello.fpr -o hello
./fpr run tests/float.fpr
```

From another architecture, use a Linux RISC-V toolchain with its sysroot:

```sh
./fpr build tests/base/hello.fpr --target=linux-riscv64 \
    --cc riscv64-linux-gnu-gcc --harts 4 -o hello-rv64
./fpr build library.fpr --target=linux-riscv64 \
    --cc riscv64-linux-gnu-gcc --module -o library.so
```

The resulting executable needs the target libc loader and libraries. The
compiler supplies `-march=rv64gc -mabi=lp64d -mcmodel=medany`. Low-level
assembly emission is `fpr compile --system=posix --target=rv64 input.fpr out.s`.
Bare-metal `--target=rv64` retains its existing register and ABI contract.
Unix RV32 is explicitly refused; the existing ESP-IDF RV32 host is unchanged.

## Runtime contract

Linux owns `tp` and `gp`. Generated executable code loads `fpr_posix_hart`
through libc local-exec TLS. Shared modules, including C helpers linked with
`--module --with`, use initial-exec TLS and PIC addressing.
Modules borrow the executable's already-present TLS cell rather
than registering a new runtime. C runtime hart reads use volatile assembly
so a pointer computed before actor migration cannot be reused afterward.

`machine/unix/ctx_rv64.S` preserves integer callee-saved registers,
`fs0..fs11` and `fcsr` in 29 words. It never restores another worker's
`tp` or `gp`. New actors start with cleared FP state and default rounding.
Cross-unit tail calls use `tail` rather than short-range `j`, allowing both
interposable shared symbols and programs larger than JAL's one-MiB reach.

QOS Portable images use `--target=qrv64`. They have no ELF loader TLS
registration, so they borrow the host TLS block through `fpr_g_tlsoff`.
QOS owns image packaging, relocation and the host HAL. No Linux syscalls or
libc references are added to the freestanding image. Executable, shared,
QOS and bare-metal unit caches have distinct identities.

## Checks

```sh
python3 tests/check_rv64_linux.py
python3 tests/check_rv64_linux.py --cc riscv64-linux-gnu-gcc --output /tmp/rv64-tests
python3 tests/check_rv64_linux.py --execute-only --output /tmp/rv64-tests \
    --runner 'qemu-riscv64 -L /path/to/target/sysroot'
```

The optional runner receives a local executable and artifact arguments and
must forward stdin and `FPR_HARTS`, `FPR_HEAP_MB`, `FPR_STACK_MAX_MB`. An SSH
upload/execute wrapper can test a real board. No assembly rewriting occurs.

On the physical 4 GiB STAR64 at `192.168.0.151`, all 17 execution cases passed:
hello, F64 arithmetic, vectors, actors, sleep/wakeup, receive/wakeup and
stdin/stderr at one and four workers; shared Int/F64 and C-helper hart TLS calls at one and
four workers; and the C context-switch ABI check. That check preserves FP
registers, rounding mode, TP and GP across twenty switches. Cross-compilation
used Buildroot GCC 14.4.0 and the board's glibc sysroot.

The complete existing macOS Base suite, module replacement/refusal/MVU tests,
x64/AArch64/RV64 shared PIC artifact checks (with LLVM clang) and ESP-IDF TLS
checks also passed. This establishes the tested Linux ABI and
runtime paths. Native GHC/compiler bootstrapping on the STAR64, other libc
implementations, RVV and other RISC-V boards have not been validated.

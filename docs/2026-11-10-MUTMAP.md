# MutMap: a linear, runtime-backed hash table

Date: 10 November 2026. Branch `perf/mutmap`, from `540ba57` (main after #57,
#58 and #59). This is priority 1.3, delivery item 4, of
[Performance priorities](2026-11-09-PERFORMANCE-PRIORITIES.md). It builds on
[callable ownership](2026-11-09-CALLABLE-OWNERSHIP.md): a closure that
captures a `MutMap` is single-use.

## Summary

- `std/mutmap` adds `MutMap 1 k v`, a hash table keyed by `Int` or `String`.
  It is LINEAR in the prelude (`MutMap 1 k v = Type Int.`), so every operation
  consumes the map and hands it back, as `Vector` does. Because of that the
  runtime writes in place.
- The runtime adds the hash primitives `strHash` and `intHash`. They are
  deterministic, unseeded and nonnegative.
- `withCapacity n` makes room for `n` entries. An insert that takes the table
  past 3/4 full doubles it first, and that insert's contract pays for the
  doubling (Vector's WCET rule).
- `freeze cmp` turns the table into the ordered, persistent `Map` in
  O(n log n). It uses the runtime sort and a new O(n) balanced build,
  `Map.fromDistinctAscList`.
- Every operation with a fixed bound declares `work`/`alloc`/`live`, and every
  declaration is PROVEN. `tests/reliability/std_contracts.py` shows 0 drift.
- Sol runs the same module through an engine (`Sol.MutMap`) that reproduces
  the native 64-bit table exactly: the same hashes and the same slot order.
- On wordfreq (2,000,000 words, 50,000 distinct), main's `Map` version takes
  4.108 s and peaks at 1992 MB. The MutMap version takes 0.477 s and peaks at
  207 MB, 8.6x faster and 9.6x smaller. On treemap the times are 1.302 s
  against 0.441 s and the peaks 614 MB against 162 MB. All are medians of 7
  interleaved runs, and the outputs are byte-identical (see Measurements).
- The capacity policy (keep charged growth only, or add a fixed-capacity mode
  with a one-probe insert bound) is an open decision for Jack; see
  "Capacity policy: decision needed".

## API (`MutMap = use "std/mutmap"`)

| Function | Type | Notes |
|---|---|---|
| `strings`, `ints` | `Unit -> MutMap String v` / `MutMap Int v` | empty, no slots allocated |
| `withCapacity` | `Int -> MutMap k v -> MutMap k v` | room for n entries with no growth; never shrinks |
| `insert` | `k -> v -> MutMap k v -> MutMap k v` | replaces an existing value |
| `insertWith` | `(v -> v -> v) -> k -> v -> MutMap k v -> MutMap k v` | `f old new` where k is present (`Map.insertWith`'s order); f is called at most once |
| `alter`, `update` | `k -> (Option v -> Option v) -> MutMap k v -> MutMap k v` | `None` removes |
| `remove` | `k -> MutMap k v -> MutMap k v` | backward-shift deletion, no tombstones |
| `insertAll` | `List (k, v) -> MutMap k v -> MutMap k v` | later pairs win |
| `get` | `k -> MutMap k v -> (Option v, MutMap k v)` | reads hand the map back |
| `getOr`, `member`, `size`, `isEmpty`, `capacity` | `... -> (r, MutMap k v)` | `capacity` = entries before the next insert grows the table |
| `fold` | `(b -> k -> v -> b) -> b -> MutMap k v -> (b, MutMap k v)` | slot order |
| `toList` | `MutMap k v -> (List (k, v), MutMap k v)` | slot order |
| `sortedList` | `(k -> k -> Ordering) -> MutMap k v -> (List (k, v), MutMap k v)` | ascending |
| `freeze` | `(k -> k -> Ordering) -> MutMap k v -> Map k v` | consumes the table |
| `thaw` | `Map k v -> MutMap k v -> MutMap k v` | the Map is untouched |
| `free` | `MutMap k v -> Unit` | storage back to the allocator |

The runtime primitives behind these (`mutmapStrings`, `mutmapInts`,
`mutmapReserve`, `mutmapInsert`, `mutmapInsertWith`, `mutmapSlot`,
`mutmapValueAt`, `mutmapSetAt`, `mutmapRemoveAt`, `mutmapRemove`,
`mutmapSize`, `mutmapCapacity`, `mutmapFold`, `mutmapToList`, `mutmapFree`,
`strHash`, `intHash`) are builtins in `compiler/Infer.hs`, the Sol VM and the
LSP's `builtins.json`.

The style is the `Vector 1` threading style:

```
counts = List.fold (fn m w -> MutMap.insertWith (fn old new -> old + new) w 1 m) (MutMap.strings Unit) ws;
(n, counts) = MutMap.size counts;
(es, counts) = MutMap.toList counts;
_ = MutMap.free counts;
```

## Ownership

`MutMap 1 k v` is linear by declaration, so the existing linear checker
enforces everything. `mutmapFold` joins `repeatedCallbackPrims`
(`Ownership/Shape.hs`), so a closure that owns a MutMap cannot be handed to a
fold. `tests/check_mutmap.py` holds 8 refusals that both native and Sol must
print, each with a legal twin that must build and print the same in both:

- using the map twice;
- dropping it;
- using the old map after an update;
- a read whose returned map is discarded with `_`;
- a capturing closure called twice;
- a capturing closure handed to `List.map`;
- a capturing closure handed to `MutMap.fold`;
- storing the map twice.

A `String` key on an `Int` map, or the reverse, is a type error. If one slips
through (see "A type-check gap found on the way"), the runtime panics
("an Int-keyed map got a non-Int key") rather than misreading memory.

## Representation (`runtime/vec.c`, `runtime/vec_layout.h`)

A MutMap is a `vec_t` with the new representation `VR_MAP = 6`, so every
runtime walker treats it as a Vector with no new case: the deep copier, the
message send, the `Sys.loop` refusal, bulk and region storage, and release.

- **Columns.** There are three, `capacity` slots each:
  - hash: raw words; 0 means empty, an occupied slot holds `h | TOPBIT`;
  - key: a raw `Int`, or a boxed `String`;
  - value: boxed.
- **Header fields.**
  - `len` is the slot count: a power of two, at least 8, or 0 before the first
    insert.
  - `eltid` is the entry count.
  - `elvar` is the key kind: 1 for `Int`, 2 for `String`.
- **Probing.** Linear probing at a load of at most 3/4. A lookup compares the
  stored hash first and the key only on a hash match.
- **Growth** doubles the slot count and re-places every entry by its stored
  hash, which compares no keys and recomputes no hashes.
- **Deletion** is backward shift. A removal pulls the later entries of its
  cluster back over the gap, so there are no tombstones and probe lengths do
  not decay under churn.

## Hashes

- **64-bit words** (the hosts, RV64):
  - `Int` keys go through splitmix64's finalizer, applied to `k + golden
    ratio`. The finalizer is a bijection, so distinct `Int` keys never share
    a full hash.
  - `String` keys go through XXH64's single-lane round and avalanche, with
    seed 0 and the length mixed in: 8-byte words, then 4-byte, then single
    bytes.
  - Both use only 64x64 -> 64 multiplies, so no libgcc helpers are needed.
- **32-bit words** (RV32): murmur3's `fmix32` for `Int` keys and `murmur3_32`
  for `String` keys.
- `strHash`/`intHash` return the hash shifted right by 2, so the result is a
  nonnegative tagged `Int`. Values from the test: `strHash "fprisc"` =
  2400402795614854473 and `intHash 0` = 4073552104164651883. Sol prints the
  same values as native 64-bit.
- Both hashes are standard, well-tested mixers. They are deterministic across
  runs and machines of the same word size, so `fold`/`toList` order and
  program output are reproducible.

**Hash flooding.** The hashes are unseeded and public. Anyone who controls the
keys (for example, words from a network request) can choose keys whose hashes
collide modulo the table size. Every such key then lands in one cluster, and
each insert probes the whole cluster. n hostile keys cost O(n^2) probes in
total, and one probe can reach C slots. The WCET contracts already charge
that worst case, a probe of at most C slots, so the bound stays sound under
attack. What an attacker can do is push the observed cost from the typical
toward the stated bound. For untrusted keys today, use `Map`, an AVL tree with
O(log n) worst case and no hashing. There are two possible remedies, and
neither is implemented:

- a per-process seed, which would give up reproducible slot order;
- the priorities document's "ordered collision fallback": clusters past a
  length limit turn into a tree.

Both are open questions below.

## Order semantics

- `fold` and `toList` visit entries in **slot order**. That order is
  deterministic for a given word size and a given sequence of operations, the
  same on every run and every machine of that word size, and Sol reproduces
  the 64-bit order. It is not key order and not insertion order, and it can
  change after any insert or remove (growth, backward shift). It also differs
  between 32-bit and 64-bit targets, because the hashes differ. A program
  whose output depends on it should sort the result or use `sortedList` or
  `freeze`.
- `sortedList cmp` and `freeze cmp` are **ascending under `cmp`**, which must
  agree with key equality (`Order.int`, `Order.string`). `freeze` sorts with
  the runtime's stable sort and builds the AVL tree in O(n) with
  `Map.fromDistinctAscList`. If `cmp` disagrees with key equality, so that the
  sorted keys are not strictly ascending, `fromDistinctAscList` falls back to
  `Map.fromList`. The result is then still a valid `Map`, as a cmp-ordered
  `Map` would be.

## Costs (WCET always on)

C is `len m`, the slot count. Every bound below is in `compiler/Cost.hs`
(`mutmapCost`) and is declared and PROVEN on the std function.

| Operation | work | alloc | live |
|---|---|---|---|
| `strings`, `ints` | 25 | 352 | 352 |
| `get` | `len k + C*(len k + 1) + 16` | 88 | 88 |
| `insert` | `len k + 7C + 2C^2 + C*(len k + 1) + 26` | `48C + 240` | `72C + 240` |
| `insertWith` | `insert` + `work f` | `insert` + `alloc f` | same |
| `alter`/`update` | two probes + growth + `work f` | `alloc f + 48C + 280` | `alloc f + 72C + 280` |
| `remove` | `len k + C + C*(len k + 1) + 1` | 0 | 0 |
| `fold` | `C*(work f + 4) + 1` | `C*(alloc f + 112) + 24` | same |
| `toList` | `C + 1` | `48C + 32` | same |
| `withCapacity n` | `C + 3S + C*S + 1`, with `S = 3*max 0 n + 8` | `24S + 48` | `24C + 24S + 48` |
| `size`, `capacity`, `free` | 1 | 24/24/0 | 24/24/0 |

- **A probe** is bounded by C slots, each comparing at most one key, so a
  probe costs at most `C*(len k + 1)` plus the hash's `len k`. The load
  factor is never 1, so a probe always finds an empty slot.
- **An insert** includes the worst case of doubling: re-placing C entries
  into 2C slots, with a walk of up to 2C for each. That is the `2C^2` term,
  and it is deliberately pessimistic. The amortised cost is O(1). The alloc
  bound covers the new columns (3 x 8 x 2C), and the live bound covers the old
  and new columns together.
- **Lengths through reads.** A read hands back the same map, so the cost pass
  aliases the returned map's length to its argument's (`sameMutMap` and
  `mutmapRead` in `CLet`). Without that, `len` of a map threaded through
  `get` would be opaque.
- **No declared bound.** `insertAll`, `sortedList`, `freeze` and `thaw` have
  no declared bound: their derived costs depend on a computed list length
  that the cost pass cannot name today.
- **The contract tool.** `tests/reliability/std_contracts.py` reports "96 declared bounds
  in 11 modules, 0 drifted, 25 with slack" on the branch. On main it reports
  "66 declared bounds in 10 modules, 0 drifted, 26 with slack".
- **The tool undercounts.** The 18 new functions declare 36 `work`/`alloc`
  bounds, but the tool counts `(name, kind)` without the module. A MutMap
  function named like one in another std module (`size`, `isEmpty`,
  `toList`, ...) is counted only once, which is why the count rises by 30
  rather than 36. Building `std/mutmap` alone with `fpr build --cost` shows
  all 36 of its `work`/`alloc` declarations PROVEN. Keying the tool by the
  module-qualified name (`get@<hash>`) would fix this. That fix is not made
  here.

### Capacity policy: decision needed

Today growth is unconditional and charged to the insert that triggers it. A
loop of n inserts after `withCapacity n` never grows. The contract cannot know
that, though: C in the insert bound is the map's current slot count, which
the cost pass tracks only when a length flows to it.

The priorities document also asks for "an option to refuse growth past a
declared capacity". There are two ways forward:

1. **Keep charged growth** (what is implemented). Every insert's bound
   includes a doubling. This is simple and always sound, but the bound for a
   map of unknown size is quadratic in C.
2. **A fixed-capacity mode.** `MutMap.fixed n` would make a map whose
   inserts never grow: an insert into a full map returns a
   `Result`/`Option`, or traps. Its insert bound would drop to one probe,
   `len k + C*(len k + 1) + O(1)` with no `2C^2`, which is what a real-time
   loop wants. The cost is a second insert signature, or a runtime refusal.

**For Jack:** keep option 1 as the default and add option 2 for WCET-critical
loops? Should a full fixed map trap or return `None`? Nothing for option 2 is
implemented.

## Sol

`compiler/Sol/MutMap.hs` is a pure simulation of the native table: the same
64-bit hashes, the same slot arithmetic, the same growth and backward shift.
It stores the slots as an `IntMap (Word64, Value, Value)` behind
`VMutMap (IORef MutMapStore)`. Sol therefore gives the same `strHash`, the
same `intHash` and the same slot order as native 64-bit.

`tests/std/solmutmap.sol` checks this against the values `tests/std/mutmap.fpr`
prints natively:

- `strHash "hello"` = 698586392370338664;
- `intHash 42` = 3419864383188818853;
- `toList` of keys 2, 1, 3 = `[(1,10),(3,30),(2,20)]`;
- 3000 mixed operations agree with `Map`.

## Measurements

Method: `bench/mutmap/measure.py`. One warm-up round, then 7 rounds of every
binary in shuffled interleaved order. Wall time is `perf_counter` around GNU
`time`, and peak RSS is GNU `time`'s `%M`. Each figure is the median of 7.

The box is x86_64 with 8 cores, load about 1 during the run. Raw numbers are
in `bench/2026-11-10-mutmap.json`, and the sources in `bench/mutmap/`.

The inputs:

- **wordfreq**: a 9,948,779-byte corpus, 2,000,000 words, 50,000 distinct,
  printing the top 10.
- **treemap**: 500,000 LCG `Int` inserts, then 500,000 lookups. The MutMap
  version freezes before its ordered `keyhash` fold, so its output is the
  same; that freeze is included in its time.

Every wordfreq binary prints byte-identical output, and so does every treemap
binary (md5 checked).

| Program | Compiler | Wall (median) | min-max | Peak RSS (median) |
|---|---|---|---|---|
| wordfreq, `Map.update` (main's version) | main | 4.108 s | 3.934-4.332 | 1992 MB |
| wordfreq, `Map.update` | perf/mutmap | 3.977 s | 3.863-4.366 | 1992 MB |
| wordfreq, `MutMap.insertWith` | perf/mutmap | **0.477 s** | 0.461-0.504 | **207 MB** |
| wordfreq, `MutMap.alter` | perf/mutmap | 0.624 s | 0.575-0.663 | 389 MB |
| treemap, `Map` | main | 1.302 s | 1.242-1.404 | 614 MB |
| treemap, `Map` | perf/mutmap | 1.328 s | 1.222-1.350 | 614 MB |
| treemap, `MutMap` (+ freeze) | perf/mutmap | **0.441 s** | 0.425-0.503 | **162 MB** |

What the numbers show:

- **wordfreq:** 8.6x faster and 9.6x smaller than main's `Map` version.
  `Map` code is unchanged between the two compilers, within noise.
- **treemap:** 3.0x faster and 3.8x smaller.
- **Against the estimate.** The priorities document estimated 0.4-0.6 s on
  wordfreq for a runtime-backed table, as an estimate rather than a
  measurement. The measured 0.477 s is inside that range.
- **`alter` against `insertWith`.** The `alter` variant is slower and
  larger: it allocates an `Option` in and out per word, plus a second probe
  for the 50,000 new words.

## A type-check gap found on the way (pre-existing, not fixed)

Rebinding a name in a body with no signature (`main`, or any function without
one) skips the type check of the rebinding. For example, `v = "x" :: v` where
`v : List Int` is accepted, and `[x, 1]` with `x` a String was accepted too.
The same happens on main at `95e2fbc`.

For MutMap this means `m = MutMap.insert "x" 1 m` on an `Int` map compiles,
and only the runtime's key-kind panic catches it. The runtime check stays for
that reason. This needs its own fix in `Infer`; it is not MutMap-specific.

## Not done

- **Ordered collision fallback and bounded probe length beyond C.** The
  priorities document asks for these. Probes are bounded by C, which is
  sound but large. No cluster limit or tree fallback exists (see Hash
  flooding).
- **A fixed-capacity mode** (see Capacity policy).
- **Key types.** Only `Int` and `String` keys are supported: the only
  constructors are `strings` and `ints`, so a `MutMap Float v` type can be
  written but no such map can be made. `Float` keys were left out on purpose,
  because of NaN and -0.0 = 0.0. Other key types would need a generic hash/eq
  API.
- **Peek reads** like `$vec.at`, which return a value without the
  `(value, map)` pair. Every read currently builds a pair, 24 bytes.

## Open questions for Jack

1. **Capacity policy:** should charged growth stay the only mode, or should a
   fixed-capacity `MutMap.fixed n` with a one-probe insert bound be added? And
   if so, should a full fixed map trap or return `None`?
2. **`freeze` takes `cmp`.** `freeze` needs the key order for the `Map` it
   builds, so it takes `cmp`. Alternatives are `freezeInts`/`freezeStrings`,
   or storing `cmp` in the MutMap at creation as `Map` does
   (`Map.strings`/`Map.ints`).
3. **Generic keys.** Should there be a hash/eq record argument so records or
   tuples can be keys, or should keys stay `Int`/`String` only?
4. **Peek reads.** Should pair-free reads (`MutMap.at`, which returns only
   the value, like `$vec.at`) be added to cut per-read allocation?
5. **Regions.** A MutMap inside a `Region` type is treated as non-copyable,
   the same as a Vector, which is the conservative choice. Should it be
   refused there explicitly instead?
6. **Seeded hashing against flooding.** Should there be an opt-in seed
   (`MutMap.seeded`), at the cost of reproducible order, or a cluster-limit
   tree fallback?
7. **The rebinding type-check gap** above: a separate fix.

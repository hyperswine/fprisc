# Cross-hart messages: profiled, then optimized

Date: 2026-10-01. Kind: profile and implementation record. Follows
[REGISTERS-AND-COSTS](2026-10-01-REGISTERS-AND-COSTS.md), which measured a 25-31x
gap between same-hart and cross-hart round trips and asked which transport
component dominates before the scheduler changes.

## How it was measured

`tools/xhart-profile.py` builds each workload twice: an ordinary build for
timing, and an `FPR_COST_PROBE` build for the breakdown. The probe's per-hart
ledger (`fpr_hart_t.x*`, a nanosecond clock `hal_probe_ns`) times each phase
of a send (copy, ARC promotion, ring push, wake), each ship to another hart
(publish, doorbell), the receiver's latency from ship to drained to running,
mailbox scan time excluding parked time, drop time, and the hart parks (count,
time parked, doorbell-to-wake latency, recorded in `park.c`). Ordinary builds
contain none of it. The workloads:

- **`rt`**: Int round trips, both actors on hart 0 (the reference) and across
  harts 0 and 1, with a latency histogram (p50, p99, p99.9).
- **`stream`**: one-way Ints into a growable mailbox.
- **`fanin`**: three senders flooding one receiver for 0.5 s, on four harts
  and contended on two (the receiver shares hart 0 with a sender).
  Per-sender counts and Jain's fairness index.

`tests/bench/xhart/floor.c` measures the floors with no runtime at all: a token
handed through one cache line by spinning threads (the cache-transfer cost),
and the same hand-off through a condition variable (an OS wake per hop).

## What the profile found (before)

Apple M4, macOS; one cross-hart round trip was 3.92 us (783.8 ms for 200,000)
against 0.13 us on one hart.

| Per hop | ns | Share |
|---|---:|---:|
| the parked target hart waking (doorbell to running) | ~2,190 | ~56% |
| the sender ringing the doorbell (`hal_ipi_send`: mutex, condition signal) | ~620 | ~16% |
| mailbox scan (49 ns, vs 27 ns same-hart) | 49 | ~1% |
| ring push + publishing the ship (vs 17 ns same-hart) | 33 + 30 | ~1.5% |
| drained to running (admission) | 64 | ~1.5% |
| message copy / ARC promotion / drop | 19 / 11 / 7 | <1% each |

Every message found the other hart already asleep in the kernel: 399,941
parks for 400,000 messages. The floors agreed. A cache-line round trip
costs 58 ns, so cache transfer was a few percent. A condition-variable round
trip costs 2,060 ns, so the cross-hart message was an OS wake plus about 1.8 us
of runtime. Mailbox scanning, shipping and copying were not the problem.
Fairness under fan-in was already exact (Jain 1.0, min/max 0.9997).

## What changed

Neither scheduling decision changed: admission, aging, donation and the run
queues are as they were. What changed is how an idle hart and a waiting actor
wait, and the layout of a channel.

1. **The posix park spins before it sleeps** (`machine/unix/park.c`). An idle
   hart watches its doorbell for `FPR_SPIN_US` (default 20 us) before taking
   the condition wait. Ringing the doorbell no longer takes a lock when
   nobody sleeps: the sleeper raises `waiting` then reads `bell`, the ringer
   raises `bell` then reads `waiting` (seq_cst, a Dekker pair), and it signals
   under the mutex only if the hart is waiting. That mutex can only be taken
   once the sleeper is inside `pthread_cond_wait`, so no wake is lost.
   `hal_ipi_clear` is a plain atomic store.
2. **An actor about to block on an otherwise idle hart re-checks first**
   (`runtime/actors.c`, `spin_until`). For up to `hal_block_spin_ns()` (posix
   `FPR_BLOCK_SPIN_NS`, default 2 us; 0 on bare metal, where `wfi` and an IPI
   are cheap) it re-checks what it waits for, with an exponential backoff
   between looks (up to `FPR_SPIN_GAP`, 64 `isb`). It does so only while the
   hart's run queue, backlog and incoming ships are empty, so no other actor
   waits behind it. A reply that lands inside the window costs no block, no
   wake, no ship and no context switches.
3. **A channel's two ends live on separate cache lines.** The producer's
   tail and ring pointer share one line. The consumer's head has its own
   (128 bytes on Apple silicon, 64 elsewhere). Each end keeps a cached view
   of the other's counter and re-reads it only when the view says full
   (producer) or empty (consumer). The consumer's check is signed:
   `receiveRes` can take past the cached view, and a recycled channel keeps
   an old one, so a view behind the head means re-read. Before this, a
   producer and consumer running at once moved the shared line on every
   message.

A bug found by the suites on the way: `chan_init` reset the counters of a
reused channel block but not the new cached views. A stale view then reported
messages that were never sent: a wrong message in `tests/std/store.fpr`, and a
segfault under the descriptor-exhaustion test. Both views are now reset with
the counters.

## Results (after; fastest of 5)

| Workload | Before | After |
|---|---:|---:|
| cross-hart round trip (200,000) | 783.8 ms (3.92 us) | 40.0 ms (0.20 us), **19.6x** |
| cross-hart latency p50 / p99 / p99.9 | 3,584 / 6,656 / 9,216 ns | 160 / 288 / 288 ns |
| same-hart round trip | 25.7 ms | 26.9 ms (unchanged) |
| fan-in, 3 senders on 4 harts | 15.7M msg/s, Jain 1.0 | 17.5M msg/s, Jain 1.0 |
| fan-in, contended on 2 harts | -- | 17.6M msg/s, Jain 1.0 |
| `tests/bench/xpingpong.fpr` (1M cross-hart) | 4,719 ms | 255 ms, **18.5x** |

The cross-hart round trip is now 1.5x the same-hart one, where it was 30x.
The performance ratchet is unchanged within noise. `xpingpong` joins it.

**The trade-off: one-way streaming to a consumer that does nothing.** With
2,000,000 messages, cross-hart streaming into a consumer with no work per
message runs at 17.1M msg/s, against 31.5M when harts always sleep at once
(`FPR_SPIN_US=0 FPR_BLOCK_SPIN_NS=0`). A sleeping consumer lets its producer
fill the ring alone and drains it in batches. A consumer that responds
within nanoseconds reads the producer's line while it is being written, and
only batching avoids that. A fixed gap between looks buys streaming back at
the price of latency: 128 `isb` gave 29.0M msg/s but a 1.0 us p50. The
backoff keeps latency instead. With 10 steps of work per message the gap is
5% (16.9M vs 17.7M), because the consumer falls behind and reads its cached
view. So the loss is confined to consumers that do nothing per message.

**Cost of spinning.** At one round trip per millisecond for 2 s, process CPU
time went from 0.10 s to 0.17 s, about 2% of one core. With all ten cores
loaded by other work, the cross-hart round trip was 66 ms with spinning and
70 ms without (busy cores do not enter the deep idle states that make OS wakes
slow): no pathology, p99 704 vs 320 ns.

**Kept:** the deterministic race tests (`tests/check_actor_claim.py`,
`check_base`'s deadpeer and taskstress legs), every FP-RISC suite, the Sol
transaction and safety checks, QOS smoke, and the full QOS `check-all.sh`
all pass.

## Not done

- Bare metal and QOS native keep blocking at once (`hal_block_spin_ns` is
  0); `wfi` with an IPI is the hardware doorbell there and was not
  profiled here.
- QOS Portable apps are untouched. Their own copy of the runtime parks
  through the host's `wfi` table entry (a timed poll), with a no-op doorbell
  (`qos/appside/hal.c`), and their machine provides no `hal_block_spin_ns`.
  Neither change reaches them, and they were not profiled here.
- The global ARC table lock taken by every send and drop was 7-11 ns
  uncontended. It was not measured under many-hart contention, where it
  could matter.

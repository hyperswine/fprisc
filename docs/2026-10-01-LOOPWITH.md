# Sys.loopWith: a loop whose every step is an arena

Date: 2026-10-01. Kind: implementation record. Motivated by QOS's launcher
(`qos/docs/2026-10-01-DISPLAY-BUFFERS.md`), which leaked one frame per
redraw.

## The problem

An actor's pool is reclaimed when the actor dies, or at an explicit
boundary. A long-lived loop that allocates a little on every turn therefore
grows without bound, even when nothing it allocates outlives the turn. That
"little" is hard to avoid:

- each `Vec.get`/`Vec.at` returns a 48-byte tuple;
- a closure passed to `Sys.arena` is allocated in the caller's pool;
- every result of `Sys.arena` is copied into the caller's pool.

Measured on posix with a two-buffer frame loop over 1,920 cells:
`Vec.set`/`Vec.put` allocate nothing, `Vec.get` allocates 48 B per call. A
frame that diffs the two buffers bumped 184 KB from the pool, every frame.

`Sys.arena` alone cannot fix this:

- It refuses a Vector result, because the vector's storage would be the
  arena. So a long-lived buffer cannot pass through it.
- Its closure and its copied result still land in the caller's pool. A
  variant that threaded a vector in and out (tried first: `Sys.arenaWith`)
  still left 128 B per frame in the caller.

## The primitive

```
Sys.loopWith : Vector -> s -> (s -> Vector -> (Bool, s, Vector)) -> (s, Vector)
```

`Sys.loopWith vec s0 step` runs `step state vec` repeatedly while it
returns `True`. Each step runs under a fresh arena (`pool_override`, as in
`Sys.arena`):

1. The next state is copied into a transfer slab of its own.
2. The arena is torn down.
3. The previous state's transfer slab goes home.

Nothing touches the caller's pool until the loop ends, when the final state
is copied there once. Memory is the live state, held at most twice, however
many steps run.

The Vector is threaded **by identity**:

- The runtime snapshots its header, column and base pointers before the
  loop and checks them after every step.
- `Vec.set`/`put`/`get`/`at` never allocate, so a step that only reads and
  writes it passes.
- A push past capacity, a fresh vector or a free would leave the buffer in
  a torn-down arena. That is refused with a message, not copied.
- The state may not hold a Vector either (also refused). The one buffer is
  the place for bulk data. Two frame buffers are the two halves of one
  Vector, swapped by flipping an offset in the state.

Linearity carries over unchanged. The step function consumes the vector it
is given and returns it, and the checker sees that as an ordinary linear
function. `Sys.loopWith` is typed in `compiler/Infer.hs` and implemented in
`runtime/runtime.c` (`g_loop_with`), beside `Sys.arena`. That code is now
`arena_open`/`arena_close`, shared by both.

## Verified

`tests/base/loopwith.fpr` (registered in `check_base`) runs a double-buffered
frame loop that also allocates garbage of its own every step:

| Steps | Caller pool grew |
|---:|---:|
| 1,000 | 224 B |
| 20,000 | 224 B |

The 224 B is the final state and the returned pair. The first loop in a
process pays a one-time 64 KiB, so the test warms up first.

Process RSS was 3.42 MB at 20,000 steps and 3.44 MB at 200,000. The same
loop without `loopWith` bumped 3.6 GB over 20,000 frames.

`check_base` also builds two programs that must be refused, and checks the
panic text: one whose step pushes past the vector's capacity, and one whose
state holds a Vector.

## Not done

- `Vec.get`/`Vec.at` still box a tuple per call. Inside a step that is
  arena garbage and costs nothing that lasts. Outside one, a compiler rewrite
  of `(x, v2) = Vec.at i v` into a non-allocating peek would remove it: the
  handle returned is always the one passed in.
- The 64 KiB first-loop cost was not traced to its source; it is constant.
- The Sol VM does not implement `Sys.loopWith`. No sketch-tier program uses
  it.

# std/hashmap as a hash trie (14 November)

Kind: implementation record. Takes the last follow-up of [the x64 performance profile](2026-11-14-PERFORMANCE-PROFILE.md)
("a real hash table behind `std/hashmap`") and supersedes the tree in
[std/hashmap and direct comparators](2026-11-14-HASHMAP-AND-DIRECT-COMPARATORS.md). The API, the names and the
contracts a caller sees are unchanged except iteration order (below).

## Why a trie and not a flat table

A HashMap is a persistent value: an insert returns a new map and the old one stays good. A flat table cannot
be that without a hidden mutable object inside a value, which copy-out, sends between actors and `==` would all
have to learn about. A hash trie is the persistent form of a table: the hash chooses the way, there is nothing to
balance, and where the map has one holder the nodes are written in place, which is what a table does.

## The structure

```
Tree k v = Type (Leaf | Tip Int k v | More Int (List (k, v)) | Node <sixteen Tree k v>).
Map k v = Type (Map (Ops k) Int (Tree k v)).
```

* `Leaf` is nothing; `Tip` one entry with its key's whole hash; `More` the entries of keys whose hashes are equal
  (ascending by the map's comparator); `Node` sixteen subtrees chosen by four bits of the hash, low bits first.
* A walker carries the shift (0, 4, 8, ...). Two different hashes differ in some four bits, so splitting two
  entries ends; equal hashes share a `More`. The depth is at most sixteen nodes and about log16 n.
* A key is hashed once; the comparator runs once per operation, at the `Tip` (or along a `More`).
* Removal leaves the nodes it emptied. `size` is counted in the wrapper, and `equal` compares entries, so neither
  sees them; a map that shrinks a great deal keeps those nodes until it is rebuilt.
* **Iteration order changed**: still deterministic and independent of insertion order, but it is now the order of
  the hashes read four bits at a time from the low end, not ascending hash. `toMap cmp` gives key order as before.

### Three primitives

A node is read and rebuilt by field NUMBER, so a walker is one small step instead of a sixteen-way match:

* `nodeGet i x`: field `i` of cell `x`.
* `nodeWith n i x v`: a copy of `x` (a cell of `n` fields) with field `i` replaced: the persistent update.
* `nodeSet i x v`: stores into `x` and answers it. The compiler puts it where it has shown one holder; `std/hashmap`
  itself uses it only on a copy it has just made.

They are runtime functions (`runtime.c g_nodeGet`, a call each) typed `Int -> a -> a` and so on: a node's fields
are all of the node's own type. An earlier draft gave them free result types; the recursive call then carried an
unsolved type variable, the callback specializer could not match it against the walker's signature, and every
specialized copy fell back to the general walker below its first level.

`fold` and `map` match the sixteen fields instead: every one is visited, and the termination checker sees the
descent on a part of `t`. The walkers that follow one child are measured by the shift (`measure (64 - s)`), with
the floor as a branch inside the node case so the body still begins with the Leaf test the owned-map rewriting
looks for.

## In place when owned

`Reuse.hs` had one walker plan, for std/map's tree (children in fields 1 and 4, `balance`, rotations). It has a
second now, `trieWalkerPlan`, for a walker that reads one child by number, recurs on it and answers
`(nodeWith n i t c2, d)`. Its twin stores into `t` (`nodeSet`). The conditions that make the store unobservable:

* the copy is the first field of a tail tuple, so nothing reads `t` after it;
* `t` is otherwise only tested, projected, read by number, or answered whole;
* the child goes only to the recursive call; what is stored is that call's tree, used once, at the number the
  child was read at. No subtree ends up under two parents.

A tail that builds `t`'s own constructor again from fields that only read `t` (a `Tip` with a new value) is built
over `t`. The recursive call may be to a walker already planned (two tiers), and the rest of the owned-map
machinery (loops, entries, region cycles, the `d == 2` contract) is the existing code: it is generic over the
walker plans. `std/hashmap` is recognised by `insGo`, `altGo` and `Leaf`, as before.

One fix outside the new plan: a lookup twin dropped the comparator parameter but left it where the walker hands
the comparator to a helper (`bucketGet`). The helper now gets the known function.

`altGo` never hands its callback to a helper (the `More` case looks up, applies `f` itself, then stores): a copy
made for one known `f` then has no `f` left at any depth.

`codegenRev` is 234.

## Results

M4, arm64, 5 interleaved rounds, medians, outputs checked. The machine was busy with other work during these
runs, so read the ratios, not the absolute times (the `std/mutmap` column is from a separate, busier run).

| program | tree by hash | hash trie | linear `std/mutmap` variant |
|---|---:|---:|---:|
| wordfreq_hashmap | 0.421 s / 242 MB | 0.252 s / 243 MB | 0.276 s / 231 MB |
| treemap_hashmap | 0.917 s / 161 MB | 0.318 s / 161 MB | 0.256 s / 160 MB |
| csv_hashmap | 0.267 s / 145 MB | 0.210 s / 149 MB | (none) |

Without the in-place twin (the persistent path alone) the trie copies about five 136-byte nodes an update:
treemap_hashmap was already twice as fast as the tree but at 482 MB, and wordfreq_hashmap was slower (0.87 s,
538 MB). A map that is NOT owned (kept versions, a map shared with another holder) pays that.

Checks: `tests/std/hashmap` (100,000 inserts and removals, 100,000 alters, forced hash ties, versions kept while
a loop updates) passes unchanged on arm64 and on x86-64 under Rosetta. `sol tests/run.sol`: all pass except
`result-sizes` (fails the same way on the unmodified tree here) and the listed `trust` known failures;
`make unit-tests`: 44 suites pass. The child number is written out in each walker (`band (BITSHIFTR h s) 15`):
a helper of its own is in stdcheck's checkable fragment, where the shift counts as an unsafe extern.

## Not done

* The three primitives are calls. Inline loads and stores (as `charAt` has) would take the node step from two
  calls to a few instructions.
* Removal does not collapse emptied nodes.
* `get` in a lookup loop walks the trie through the general `getGo` unless the lookup twin applies.

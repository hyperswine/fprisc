# I64: a 64-bit integer type beside Int

Date: 2026-10-05. Kind: implementation record. Applies from revision
`db42acd` plus this change. Answers the first issue in
[2026-10-05-WASM-STYLE.md](2026-10-05-WASM-STYLE.md): `Int` is a tagged
63-bit value, and code that needs exact 64-bit arithmetic had to split
values into halves by hand.

## The type

`I64` is a 64-bit two's-complement integer. It **wraps** on overflow, as
C's `uint64_t` and wasm's `i64` do. That is its contract, and the reason
it is a separate type rather than a wider `Int`. `Int` is unchanged.

| Group | Operations |
|---|---|
| operators | `+ - * /` (signed, truncating), `%` (C remainder: the dividend's sign), `< > <= >=` (signed), `== !=`; `^` is refused |
| unsigned | `I64.divU remU ltU gtU leU geU`, `I64.strU` |
| bits | `I64.and or xor not neg`, `shl shr` (logical) `sar rotl rotr` with an `Int` count taken modulo 64, `clz ctz popcnt` (to `Int`) |
| with Int | `I64.ofInt` (every Int fits); `I64.toInt : I64 -> Result Int String` (refuses what does not fit 63 bits); `I64.fromParts hi lo` and `I64.hi`/`I64.lo` (unsigned 32-bit halves) |
| with F64 | `I64.toF64`, `toF64U` (round to nearest); `I64.ofF64`, `ofF64U : F64 -> Result I64 String` (truncate; refuse NaN and out of range); `I64.ofF64Bits`/`toF64Bits` (the IEEE bits, wasm's reinterpret) |
| text | `I64.str` (also what `print`, `str` and interpolation use), `strU`, `hex`; `I64.parse : String -> Result I64 String` (sign, `0x`, `_` separators; refuses past 64 bits, wraps past the signed range as a wasm literal does) |

There are no `I64` literals: write `I64.ofInt 5`, or
`I64.parse`/`I64.fromParts` for values past 62 bits. `I64` never mixes
with `Int` implicitly; `I64.ofInt 1 + 2` is a type error.

Division by zero and `INT64_MIN / -1` panic, as `Int`'s `/` does.
`INT64_MIN % -1` is 0.

## Representation: boxed, on purpose

The first version held an `I64` as the raw machine word, as `F64` is.
It failed a direct test. `send` of a structure holding the value
`2^40 + 4096` hung the program until it was killed. On this Mac the heap
lies near 2^40, so the copier's `fpr_in_heap` took the integer for a
pointer and followed it. Floats share that hazard only as rare denormals
(the comment above the float primitives in `runtime.c` records it).
Integers land there routinely: Unix time in milliseconds is about 2^40.6.

So an `I64` is a boxed cell, `bits_t {T_BITS, variant 4, 64, value}`.
Every value walker already treats `T_BITS` as a leaf: send, drop, keep
and arena copy-out copy it by size; `==` compares its value; render prints
it as a signed decimal. As a result an `I64` may sit in lists, tuples,
records, vectors and polymorphic code, be printed inside them, and be sent
between actors. `tests/i64.fpr` sends values near 2^40 and `INT64_MIN`
and gets them back.

## What it costs

Ten million multiply-add steps, on this Mac (arm64), built with `fpr build`:

| | time | peak memory |
|---|---|---|
| `Int` | 0.29 s | 2.9 MB |
| `I64` | 0.37 s | 1.9 GB |
| `I64`, 100 chunks of 100,000 steps, each under `Sys.arena` | 0.46 s | 22 MB |

Each result is a new 24-byte cell, and the runtime reclaims nothing
within an actor's run outside an arena; the same is true of any allocating
loop. A long `I64` loop belongs under `Sys.arena` or `Sys.loopWith`.

## Where it lives

- `compiler/Infer.hs`: the type, the primitive signatures, and `I64`
  in operator resolution (operators, `%`, `==`, `str`/`print`).
- `runtime/runtime.c`: the primitives, as `FPR_FN(fpr_g_I64_x2e...)`, so
  each is called directly when saturated and is a first-class value
  otherwise. They sit inside the 64-bit-only section. On a 32-bit target
  a use of `I64` is a link error, and the builtin profile on RV32 refuses
  it by name (`compiler/Compile.hs`).
- `runtime/runtime.c` `veq`: variant 4 compares by value beside Word and
  Addr. `runtime/fpr.h` documents the variant.
- `tests/i64.fpr` (50 cases) and the I64 leg of `tests/check_base.py`,
  which also checks that `I64` does not mix with `Int`, that `^` is
  refused, and that division by zero panics with its message.

## Checked

`tests/check_base.py`, `check_cases`, `check_float_inline`,
`check_arc`, `check_builtin`, `check_cost`, the Sol examples (21),
`tests/float.fpr`, and the WASM suite (57 of 57) all pass after the change.

## Not done

- **Code generation:** no inline paths for `I64`. Every operation is a C
  call and an allocation. Unboxing in specialized loops would remove both.
- **Sol:** no `I64` in the Sol profile.
- **Literals:** no literal suffix.
- **Vectors:** no raw `I64` vector column. Vectors hold boxed cells.
- **32-bit targets:** no `I64` on the ESP32-P4 or on any 32-bit target.
- **WASM VM:** `examples/wasm/` still uses its two-halves i64. Moving it
  to `I64` would remove about 150 lines.

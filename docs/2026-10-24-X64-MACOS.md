# macOS x86-64 target

Date: 2026-10-24. Kind: implementation and validation record.
Base: main `13ff336` (after the [typed generator retirement](2026-10-23-TYPED-GENERATOR-RETIREMENT.md)).
Branch `typed-ir-retire`.

Hosted x86-64 was only ever Linux ELF: the deleted translator and the typed
selector both read the hart and the argument seven/eight cells with
`%fs:cell@tpoff`, put data in `.rodata` and named C symbols without
Mach-O's underscore. Yet `--system=posix` on an Intel Mac routed to that
backend, so a build there failed in the assembler with one error per hart
read (749 for `tests/actors.fpr`). The C runtime was never the problem: all
of `runtime/` and `machine/` compile for macOS x86-64 unchanged.

A diagnosis first rewrote that ELF output textually (Mach-O section and
symbols, plain globals for the cells, one hart). Under Rosetta it matched the
AArch64 build on actors, float, deep, bigframe, fmath, eq and fanin: the
selection, frames, stack growth, traps and runtime contract needed no change,
only the object-format and thread-local spellings.

## The target

- `fprc --target=x64mac`, and `--system=posix` on a `darwin/x86_64` host,
  select the typed x64 backend with Mach-O output. `fpr build
  --target=macos-x86_64` builds one from any Mac: it passes `-arch x86_64`
  to the Mac's own clang for the runtime and the link, needs no `--cc`, and
  keys the runtime object cache by those flags. Modules (`--module`) build
  the same way.
- `Codegen.Target.X64` has a third hart form, `HartTlvMachO`, which also
  names the format (`x64Format`): C-visible symbols take the underscore,
  `.L` locals become `L`, a library unit's weak functions are
  `.weak_definition`. Unit data uses the existing `Common.dataSyntax MachO`
  (`__DATA,__const`, the same rules as Apple Silicon); `DirectX64` carries
  the object format for that.
- The hart and the two argument cells stay ordinary C `__thread` variables
  (`machine/unix/main.c`), which Mach-O implements as TLV descriptors. Each
  access is the documented descriptor call:

      leaq -32(%rsp), %rsp            # rax, rdi, rbx kept in a block below rsp
      movq %rax, 24(%rsp); movq %rdi, 16(%rsp); movq %rbx, 8(%rsp)
      movq %rsp, %rbx; andq $-16, %rsp
      movq _fpr_posix_hart@TLVP(%rip), %rdi
      call *(%rdi)                    # the thunk returns the address in rax
      movq %rbx, %rsp
      movq (%rax), %rax; movq %rax, (%rsp)
      movq 8(%rsp), %rbx; movq 16(%rsp), %rdi; movq 24(%rsp), %rax
      movq (%rsp), %r10; leaq 32(%rsp), %rsp

  The thunk preserves every register but rax and the flags (the contract
  clang's own TLV accesses rely on). The sequence preserves everything but
  its destination and the flags; cell accesses happen at arrival, while
  staging a call and in the entry sequence, never inside a flags window, and
  generated code keeps nothing below rsp. rsp is aligned through rbx because
  the reservation stage of a sized frame runs at a different alignment from
  the function body.
- `machine/unix/ctx_x64.S` spells `fpr_ctx_switch` through the same `SYM`
  macro as `ctx_a64.S`.
- The unit cache tag is `x64macr10` (`module-x64macr10` for modules), so
  ELF and Mach-O units never share a cache entry. Linux and QOS x64 output is
  unchanged, so `x64SelectionRev` stays 22.

## Cost

Every function entry reads the hart for its stack check and fuel tick, so
the descriptor call is on the hottest path. Under Rosetta on the M4, `fib 37`
(about 78 million entries), median of seven runs:

| Hart access | Time |
|---|---:|
| Darwin TLV descriptor call (this target) | 0.321 s |
| Plain global, one hart (diagnosis build, not a valid multi-hart form) | 0.158 s |
| Native AArch64 (x28) | 0.150 s |

So the documented form roughly doubles call-heavy code. These are Rosetta
timings, not Intel hardware. Two follow-ups would remove most of it: reading
the thread's TLV slot directly through `%gs` (one load, as on Linux, but it
relies on Darwin's undocumented TSD layout), or keeping the hart in a
reserved register as AArch64 does with x28 (needs every C object built so it
never uses that register, which clang offers on AArch64 but, as far as this
record has checked, not on x86-64).

## Tests

- `tests/check_x64_macos.py` (Base, macOS only): a probe compiled in strict
  mode with `--target=x64mac` has no ELF TLS, no `.rodata`, no `.L` labels,
  underscored symbols, TLV reads of the hart and of the argument seven and
  eight cells, and its own `x64macr` cache identity; every unit assembles as
  x86-64 Mach-O. With an x86-64 Mac or Rosetta, it builds programs with `fpr
  build --target=macos-x86_64` and runs them with the real runtime and the
  default hart count. On Apple Silicon the native AArch64 build of each is
  the oracle (same stdout, same status); on an Intel Mac the native build is
  this target, so status and the probe's own result are the check.
- `tests/KernelIR.hs` covers `DirectX64 MachO` in the whole-unit refusal
  probe.

## Validation (this Mac, arm64, Rosetta)

- Linux x64 and QOS x64 output is byte-identical before and after the
  change for actors, float, bigframe and logbook (root and prelude units,
  31,000 to 582,000 lines each).
- `check_x64_macos.py --require-execution`: emission (270 typed functions)
  and eight programs plus the arity-10 probe, all matching the AArch64
  build.
- Every hosted program in `tests/` built both ways and run with the default
  hart count: 53 of 65 identical in stdout and status. Eight do not build
  for AArch64 either (stale sources such as `deepsend.fpr`). Four differ only
  in run-to-run values: `memory` and `msgpack` print scheduling counters that
  also vary between two AArch64 runs, and `clientlive` and `liveutilities`
  are servers that print their port and run until the harness timeout.
- `check_posix_modules.py` with every build retargeted to `macos-x86_64`:
  x86-64 dylibs load into an x86-64 host and pass the real-module and live
  MVU checks on one and four harts, so a module's `@TLVP` reference to the
  host's thread-local cells binds through dyld.
- Unchanged checks: `check_x64_local.py --require-execution`,
  `check_x64_qos.py`, `check_x64_retirement.py`, `check_posix_modules.py`,
  `check_native_data.py`, `check_native_required.py`,
  `check_typed_ir_kernels.py --require-execution` and the selected-IR and
  allocation units of `check_typed_ir_x64.py` (its execution leg needs a
  Linux x86-64 host).
- `check_base.py -j 4`: all 124 jobs, including the new one, in 481 s.

Not verified: an Intel Mac (compiler and programs running natively on x86
hardware), x86 performance, and QOS (no QOS image on macOS x86-64).

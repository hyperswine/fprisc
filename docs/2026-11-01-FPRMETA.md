# fprmeta: the toolchain manager and launcher, first slice

Status: on branch `fprmeta`, 1 November 2026. Not merged, not published, and
no Homebrew formula yet. This is step 2 of the
[toolchain manager proposal](2026-11-01-TOOLCHAIN-MANAGER.md), with exact pins.
Evidence: [evidence/2026-11-01-fprmeta-acceptance.json](evidence/2026-11-01-fprmeta-acceptance.json).

## What there is

`tools/fprmeta/` is one FP-RISC program. It is built with `make fprmeta` into
`build/fprmeta/fprmeta`, and acts according to the name it is started under:

| name | does |
|---|---|
| `fprmeta` | manages FP-RISC toolchains in `~/.fpr` (`FPRMETA_HOME` overrides) |
| `qosmeta` | manages QOS SDKs in `~/.qos` (`QOSMETA_HOME` overrides) |
| `fpr`, `sol` | run the chosen toolchain's command |
| `qos` | runs the chosen SDK's command |

```sh
fprmeta install --archive fprisc-0.12.0-macos-arm64.tar.gz   # SHA256SUMS beside it, or --sha256 HEX
fprmeta install 0.12.0 --index FILE|URL                      # or FPRMETA_INDEX; newest when no version
fprmeta list
fprmeta default 0.12.0
fprmeta which [fpr|sol]       # the binary this directory would run, and which rule chose it
fprmeta pin [VERSION]         # rewrite this project's pin to "=VERSION"
fprmeta uninstall 0.12.0
fpr +0.12.0 build             # one command on a named version
```

The launcher picks a version in this order:

1. `+VERSION`;
2. `FPR_TOOLCHAIN` (`QOS_SDK` for `qos`);
3. the nearest `fpr.toml` (`[toolchain] fpr`) or `qos.toml` (`[sdk] version`)
   at or above the current directory;
4. the default in `settings.toml`.

It then `exec`s `HOME/VERSION/bin/NAME`. A missing version stops with exit 2
and names the install command. A launch never downloads anything.

### Pins

- `fpr = "0.12.0"` means 0.12.0 or the newest installed 0.12.x after it.
- `fpr = "=0.12.3"` means exactly that release.
- `compiler/Project.hs` understands both forms. A compiler run directly, not
  through the launcher, refuses a project pinned exactly to another release
  (exit 2, "the project asks for fpr exactly 0.13.1"). `fpr new` still writes
  a compatible pin, and `renderManifest` writes the note "exactly this fpr"
  for an exact one.
- **Pre-releases.** A compiler knows only its release number. So the compiler
  checks `=0.13.0-rc1` as 0.13.0, and the launcher is what tells `0.13.0-rc1`
  from `0.13.0`. For the same reason, a pre-release satisfies a compatible pin
  on its release (the rc1 compiler calls itself `fpr 0.12.0`), the same rule
  `Project.hs` already applied.

### Installing

Each install goes through these steps:

1. Check the archive's SHA-256 (`--sha256`, its `SHA256SUMS`, or the version
   list's entry).
2. Take the lock.
3. Unpack into `HOME/tmp`.
4. Compare every file with the archive's own inventory:
   `toolchain.json`'s `files`, or a QOS SDK's `files.sha256.json`.
5. Add `bin/fpr` and `bin/sol` links if the archive lacks them.
6. Remove write permission.
7. Rename the folder into place.
8. Write `receipts/VERSION.json`.

The first version installed becomes the default. Uninstalling the default
clears it.

A version list is JSON:

```json
{"format": 1, "entries": [{"component": "fprisc", "version": "...", "platform": "macos-arm64", "url": "https://...", "sha256": "...", "yanked": false}]}
```

Entries for another component or platform are skipped, and so are withdrawn
ones (`yanked`).

## Decisions and findings

- **Written in FP-RISC, launcher included.** A native FP-RISC program that
  only `exec`s costs 4.3 ms more than running the real compiler directly
  (median of 25: 23.7 ms against 19.4 ms). The shell wrapper tested on 30
  October cost about 7 ms, and it broke absolute shebangs. The binary links
  only `/usr/lib/libSystem.B.dylib`.
- **New primitive `Sys.name`** (`Program.name` in `std/program`). It is the
  last part of `argv[0]`. `Program.args` drops it and `Proc.self` follows
  links, so a multi-call binary could not tell `fpr` from `sol` before this.
  It is POSIX only: the Tang Nano receives its arguments over RPC and has no
  program name, and a board program that used it would fail at link time,
  by name.
- **System tools for what std lacks.**
  - `tar` unpacks;
  - `shasum` hashes (`std/digest` runs at about 1 MB/s, too slow for a
    20-70 MB archive);
  - `ln` and `chmod` handle links and permissions;
  - `curl` downloads (HTTPS or `file://` only).

  `std/httpclient` holds a whole response in memory and doesn't follow
  redirects. GitHub release downloads redirect.
- **The lock is `/bin/mkdir HOME/lock`.** `Os.mkdir` (`machine/posix/os_fs.c`)
  treats an existing directory as success. So it cannot be a lock: the first
  version of the code took a held lock and then deleted it, and the
  acceptance check now catches that.
- **No signatures yet.** `std/crypto` verifies Ed25519 through OpenSSL
  (`machine/unix/crypto_openssl.c`). Linking it would bring a Homebrew
  library back into the manager. Step 4 (publishing) needs either Ed25519
  verification without OpenSSL, or Apple's own crypto on macOS. Until then a
  version list protects only against corruption, not against a tampered
  list.
- **QOS 0.2.0 installs and builds through `qosmeta` as it is.** Its archive
  carries a relative `bin/qos` script. That script still needs Python 3.11+
  on `PATH`, and the SDK's compiler still loads Homebrew's libgit2 and
  libarchive. Both are fixed by the
  [QOS proposal](https://github.com/hyperswine/qos/blob/main/docs/2026-11-01-SDK-PROCESS-APPS.md)
  and by self-contained archives.

## Acceptance

`tools/fprmeta-check.py --old A --new B [--qos C] --output DIR` ran with the
two published-series archives `0.12.0-rc1` and `0.12.0`, plus the published
QOS 0.2.0 archive. Everything ran under `sandbox-exec`, with the workspace,
GHC, Cabal, the real `~/.fpr` and `~/.qos`, `make` and `git` denied. It
passed 31 steps:

- **Refusals.** Nothing chosen exits 2 with the install hint. Also refused: a
  wrong checksum, a tampered archive (its own checksum right, its inventory
  wrong), a duplicate install, and a held lock (which stays in place).
- **Choosing a version.** The first install becomes the default. 0.12.0 came
  from a version list, with a withdrawn entry and a foreign-platform entry
  skipped.
  - A compatible pin found from a subdirectory chose the old version, then
    moved to the new one once it was installed.
  - `fprmeta pin` wrote an exact pin, which stayed on the old version.
  - `FPR_TOOLCHAIN` and `+VERSION` overrode the pin.
- **Reproducible builds.** The exactly pinned project rebuilt byte-identical
  after the newer version was installed. The output name is part of the ad
  hoc code signature, so the check rebuilds under the same name.
- **Sol through the launcher.** Arguments, including an empty one and one
  with a space, arrived intact with `#!/usr/bin/env sol` and with
  `#!/abs/path/sol`.
- **Uninstalling.** Removing the old version left the project and the build
  cache byte-identical, and the built program still ran. The exactly pinned
  project then stopped with `fprmeta install 0.12.0-rc1`.
- **QOS.** `qosmeta` installed QOS 0.2.0, then `qos --version`, `qos new` and
  `qos build` worked through the launcher.

Unit tests: `make unit-tests UNIT=ProjectWorkflow` covers exact pins (match,
mismatch, pre-release, refusals, render/parse round trip).

## Not done yet

- **Signatures** and a published version list (step 4), and the `fprmeta` and
  `qosmeta` Homebrew formulas.
- **`fprmeta gc`.** The launcher doesn't yet record when it last ran each
  version.
- **Linux.** `tools/fprmeta` calls `/usr/bin/shasum`, `/usr/bin/tar`,
  `/bin/ln` and `/bin/chmod` by path. Linux needs `sha256sum` and its own tool
  paths. `platform` already maps `aarch64` to `arm64`.
- **Withdrawn versions.** `install 0.0.1` names the available versions but
  doesn't say that 0.0.1 was withdrawn.
- **Self-contained archives.** The `0.12.0` archives still load Homebrew's
  libgit2 and libarchive. The `self-contained-toolchain` branch fixes that for
  the next release.

# Application workloads: terra-ii, pos1, inventory (2026-11-18)

Do the apps hold up, not just the 16 benchmarks? Three fprisc builds on the same box
(x86-64, 8 cores, no hardware counters):

| tag | fprisc | what it has |
|---|---|---|
| old | 18fce327 | the 2026-11-16 overhead-audit baseline |
| mid | 830cb768 | after the quick fixes, C1/C3/C7/C10, R2, unboxing stages |
| new | e4e8476c | + closure callbacks, raw I64 locals, string runtime, C9 regalloc 1+2, shallow-stack leaves |

Method: callgrind instructions, median of 3 (at most 2 lanes; every spread is under 0.003%).
Wall: 5 interleaved rounds on an idle box (pos1 sessions: 3 rounds). Outputs are compared
for every run. Raw data, drivers and scripts are in [2026-11-18-apps/](2026-11-18-apps/). The non-Sol
helpers are stored as `.txt` and ran from outside the repo.

## Summary

| workload | old | mid | new | old→new |
|---|---|---|---|---|
| terra-ii logic, checks-only build (instr) | 4.678 G | 4.399 G | 4.050 G | −13.4% |
| terra-ii logic, full pipeline (instr) | OOM at compile | 3.500 G | 3.338 G | mid→new −4.6% |
| inventory boot + add member (instr) | 16.597 G | 11.287 G | 10.176 G | −38.7% |
| inventory boot + import 300 (instr) | 24.321 G | 18.944 G | 17.280 G | −28.9% |

| pos1 websocket session, 300 checkouts (wall) | 21.66 s | 6.31 s | 6.42 s | −70% (see attribution) |

No measured regression from old to new. Every output matches across the three builds.

## terra-ii (hyperswine/terra-ii ca41f8d)

**Gap:** the real `qos build`/`qos run` and the Sol GUI test need the QOS Portable SDK, which
means an aarch64 app side (link-qosapp-a64.ld, ctx_a64.S) plus clang and lld. The box is x86-64
with no clang, lld or qemu, so the 3D game, the GUI harness and the SDK-built headless test
were not run.

**What I ran instead:** a hosted x86-64 logic driver, `terra-drive.fpr.txt`. It is
tests/headless/game.fpr minus its real-disk legs (QOS Files/endpoint IPC), plus a 60-round
match and 1000 matches driven by an LCG over the game's own keys (300 under callgrind).
- Sources: the repo's src/, and qos origin/main 2770f45 `programs/mods`.
- `mods/sfx` is overlaid with `sndPlay` stubbed. This touches only the host synth call; the tone data is unchanged.
- `std/game` from e4e8476c is copied into old/mid homes, because 18fce327 has no std/game and 830cb768's lacks Latest jobs.
- Builds were made two ways: as the game ships (`optimize = "checks-only"`, i.e. FPR_NO_SPEC/INLINE/REUSE/VEC_PEEK/VEC_FUSE/RECEIVE_TURNS) and with the full pipeline.

**Correctness:** all five binaries print 32 `ok`, 0 FAIL, identical output (match digest 651888057).

| | old | mid | new |
|---|---|---|---|
| instr, checks-only | 4.6778 G | 4.3994 G | 4.0499 G |
| instr, full | — | 3.5004 G | 3.3376 G |
| wall, checks-only, 1000 matches | 3.194 s | 3.104 s | 3.098 s |
| wall, full | — | 1.238 s | 1.176 s |
| max RSS, checks-only / full | 3991 MiB / — | 3992 / 47 MiB | 3992 / 47 MiB |
| compile, checks-only | 19.5 s, 419 MiB | 18.5 s, 440 MiB | 19.0 s, 423 MiB |
| compile, full | **OOM-killed at 13.0 GB after 227 s** | 41.3 s, 864 MiB | 42.5 s, 862 MiB |

- Checks-only wall barely moves although instructions fall 13%: user time is about 1.5 s of
  the 3.1 s. The rest is page faults on about 4 GB of heap, because with REUSE off the run keeps about 4 GB
  for 1000 matches in every build. The full pipeline needs 47 MiB and is 17.6% fewer instructions
  than checks-only on new. Now that the full pipeline compiles in 42 s / 862 MiB (old could not),
  terra could reconsider checks-only. Before switching, compile the whole game, not just the logic, under the 2 GiB `compiler-memory-mb` bound.

## pos1 (fprisc examples/pos1.fpr; no separate repo)

pos1 is only examples/pos1.fpr (+pos1_core, pos1_pricing, std/journal). The QOS original is
qos/programs/pos1.fpr. All three builds compile the **18fce327 pos1.fpr source**, so the app
code is fixed. Later pos1.fpr only adds `G.cutKids` on receipt rows.

**Session workload** (`pos1drive.py.txt`, adapted from qos tests-host/pos1-check.py to std/live's typed wire):
1. Boot on a 23,460-line log (20,000 sales, 1,000 voids, restocks, price changes).
2. Sign in, then 300 checkouts (ClientState cart + Cash), every 10th voided, a restock every 50.
3. `get revenue`, then `rebuild`, then Quit.

**Correctness:** in all 9 sessions the new log lines, with timestamps normalised, are identical (md5 a2202314…). Each shows revenue 564238.40 over 20300 sales and "stock matches the log".

| session (median of 3) | old | mid | new |
|---|---|---|---|
| 300 checkouts, wall | 21.66 s | 6.31 s | 6.42 s |
| server CPU (user+sys) | 22.49 s | 7.48 s | 7.44 s |
| checkout round trip p50 / p90 | 61.5 / 72.5 ms | 17.4 / 20.1 ms | 18.3 / 20.5 ms |
| rebuild (fold 20,300 sales) | 515 ms | 397 ms | 383 ms |
| boot fold (self-timed) | 332 ms | 387 ms | 318 ms |

**Attribution:** 498ca1db (between old and mid) changed std/view: a Set in nubEntries instead
of a quadratic scan per render. That is a library fix, not overhead work. Building old's compiler
with 830cb768's std/view, encoding and livejs gives 9.14 s / 9.83 s CPU / 26.3 ms p50, against new's
6.62 s / 7.69 s / 18.0 ms in the same interleaved runs. So the compiler/runtime work accounts for
about −28% session wall and −22% server CPU; the library fix accounts for the rest (21.7 → 9.1 s).

**mid → new:** wall +1.7% and p50 +5%, but server CPU −0.5%. The batch callgrind is −3.3%. Wall varies
by up to ±5% across runs here, so I read this as flat, not a regression.

**Callgrind:** the server cannot run under valgrind. Its register misses its answer deadline
("live: the register did not answer: deadline exceeded"), so instructions come from a batch
driver, `pos1-drive.fpr.txt`. It imports pos1, folds the log 3 times (boot + rebuild) and
`commit`s 2001 checkouts with voids and restocks. Output is identical across builds:
3.6490 → 3.3947 → 3.2821 G.

**Compile** (compile-budget method: `fpr compile --system=posix`, +RTS -t):

| | old | mid | new |
|---|---|---|---|
| GHC bytes allocated | 66,511,746,104 | 66,922,029,880 | 68,220,784,040 (+2.6%) |
| max_bytes_used | 586,146,296 | 544,120,752 | 528,422,496 (−9.8%) |
| wall / max RSS (`fpr build`) | 81.8 s / 1804 MiB | 88.4 s / 1670 MiB | 83.9 s / 1641 MiB |

Allocation is within the 10% budget gate. Wall is noisy because old and new ran concurrently. On the compile-budget run, sequential and beside callgrind, it was 77.6 / 76.5 / 75.8 s.

## inventory (hyperswine/inventory cba3771)

**Sol test** (`sol project.sol test`: native checks + real loopback HTTP 200 + title): PASS on old
and new. 163.5 s and 163.8 s, run concurrently.

**Workloads:**
- member: the app's own `--member` path on a 16,001-line journal (5,000 items, 10,000 moves, 1,000 deletes). It boot-folds the journal, does 200 sha256 rounds, appends and exits.
- import-300: `--import` of 300 Firestore docs onto the same journal, deduplicated against 4,000 live items.

**Correctness:** all runs print the same counts. The 9 import outputs are byte-identical (md5 9aabf0b5…).

| | old | mid | new |
|---|---|---|---|
| member instr | 16.597 G | 11.287 G | 10.176 G (−38.7%) |
| import-300 instr | 24.321 G | 18.944 G | 17.280 G (−28.9%) |
| member wall | 2.659 s | 2.369 s | 2.286 s (−14%) |
| import-300 wall | 4.072 s | 3.794 s | 3.646 s (−10%) |
| max RSS member / import | 1963 / 3321 MiB | 1967 / 3325 | 1967 / 3325 |
| compile (`fpr build`) | 81.1 s / 1893 MiB | 82.3 s / 1744 MiB | 82.9 s / 1714 MiB |

**Found, not a regression:** memory grows with work in both builds.
- The boot fold of the 16k-line journal peaks at about 1.96 GB RSS.
- Import adds about 4.5 MB per document.
- The full 3,000-doc import is OOM-killed at about 13 GB on old *and* new.

Wall gains trail the instruction gains because a large share is sys time spent faulting that heap in. This is the next thing to look at for inventory (and for pos1's boot, 1.2 GB for the driver).

## Caveats
- terra-ii: logic only, hosted x86-64, not the QOS Portable aarch64 build or the 3D/GUI harness. std/game is held at e4e8476c for all builds.
- pos1: no separate repo. The session is one register on loopback. The Python client's JSON decoding of 260–280 KB reshape frames is inside the round trip; server CPU is the cleaner number.
- Wall numbers on a shared VM have ±5% run-to-run spread; callgrind spreads are under 0.003%.
- origin/main has moved past e4e8476c (54c812d8); not measured.

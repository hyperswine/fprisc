## Dropped or not done, and why

- **pos1 `Vector 1`**: the only linear local list (`splitEq`) measured +9.9% instructions as a Vector, so it was dropped. Every other append or index site is a model field kept alive by MVU.
- **inventory `Vector 1`**: the end-appends (`noteKind` on the profile, `addTag`) are model fields or lists of a few tags, and there are no index-heavy linear lists. So no Vector conversion. MutMap was the right linear structure for the table-like uses.
- **terra**: hands, rows, keys, out, queue, fx and log are model fields that `update` keeps alive (`syncHint m msg m3`, `captured m m4`), so they were left alone as instructed. `nth`/`setAt` only touch those shared 5-slot rows.
- **grapher**: no PR. The only append (`List.append m.points [...]`) is on the MVU model field. The render does `Vec.fromList m.points` and then `Vec.toList` straight away inside `plot`, and its cost is the per-cell `P.contains` list scan (41×21 cells × points), which is not a linearity problem. The desktop app can't run here.
- **qrepo**: the reverse/accumulate loops are already linear in their sizes and are TRMC'd. Myers' frontier is kept in `trace` at every step, so it isn't linear.
- **Not measured on 631b67e7**: the fprisc PR branch is on the newer main, which doesn't touch examples/. The numbers come from the f5a6bd9d compiler.

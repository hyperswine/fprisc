# std/ui: layout and appearance as the application's own words

Date: 2026-10-15. Kind: implementation record. Step 2 of
[2026-10-15-DESIGN-GOALS-REVIEW.md](2026-10-15-DESIGN-GOALS-REVIEW.md);
the shape it proposed, built.

## What it is

```
UI = use "std/ui".
page model = UI.page True { UI.stack | gap = 4, pad = 4, fill = UI.Screen } [
    UI.hstack { UI.stack | justify = UI.Between, align = UI.Center } [
        UI.label { UI.txt | size = UI.Title } "Inventory",
        UI.space Unit,
        UI.button { UI.btn | kind = UI.Primary } [G.send codec Save] "Save" ],
    UI.scroll { UI.stack | gap = 3, fill = UI.Grow } (List.map card model.notes) ].
```

- **Nodes**: `vstack`, `hstack`, `scroll`, `space`, `page`; `label` (fixed
  text, a static) and `text` (a model value, a dynamic slot); `button`,
  `input` (a text area when `rows > 1`); `card`, `rule`; `keyed`. Each
  takes an attribute record and children, or attributes then text.
- **Attribute records with defaults**: `stack`, `txt`, `btn`, `field`,
  `panel` are ordinary values; a call overrides fields by record update.
  There is no optional argument and nothing is a string.
- **The vocabulary**: `Align` (Start Center End Stretch Baseline),
  `Justify` (Lead Middle Trail Between Around Evenly), `Fill` (Natural Grow
  Wide Screen), `Scale` (Hero Title Heading Body Caption Tag Mono), `Tone`
  (Ink Muted Faint Accent Danger Success Warning OnAccent), `Kind` (Plain
  Primary Quiet Destructive). `gap` and `pad` are steps on the spacing
  scale (0 to 6: 0, 4, 8, 12, 16, 24, 32 px), never pixels.
- **Variants** are typed: `vary = [UI.OnNarrow [UI.GapOf 1, UI.Hidden]]`,
  with `OnWide` and `OnHover`, and the `Tweak`s are the same words as the
  records.
- **Events** are std/view's typed ones, passed to `button` and `input` as
  attributes: `G.send codec Msg`, `G.sendWith codec Msg @Client.q`,
  `G.bind @Client.q`, `G.setTo @Client.open "1"`. The message VALUE travels;
  the codec stays explicit because that is how std/view types it. `*With`
  forms (`vstackWith`, `cardWith`, `pageWith`) take std/view attributes for
  keys, locals and `showIf`.
- **Theme**: `page light` owns the token scope (std/ma's day or night
  tokens: `tx-1`, `bg-surface`, `bd-subtle`, `ac`, `danger`, ...), so a
  page built here and Ma components in it share one palette during the
  move. `UI.css tree` is the stylesheet.

## How it lowers

Every node becomes the `std/view` tree the hand-written utilities give:
`Ma.element` (the per-node box reset) with one `utilities` list of typed
declarations, variants as `narrow`/`wide`/`hover` utilities, and nothing
else. `tests/std/ui.fpr` renders a page and checks the declarations per
property (each is its own atomic class), that a `text` is a dynamic slot,
that no class string or raw property reaches the stylesheet, and that
`UI.vstack { UI.stack | gap = 3, pad = 4 } kids` renders, statics,
dynamics and stylesheet, identically to the hand-written column. The
generator, the live diff, keys and the wire format are untouched.

## What it does not do yet

- Icons, images, links, tables, select and checkbox inputs: added when an
  app's rewrite needs them, not before (step 3's list).
- A theme as a value of its own (palette and scale chosen by the
  application): the tokens are std/ma's for now, by name.
- Retiring std/ma: its components stay until no application uses them;
  std/ui is its successor, with records where Ma has positions and
  without the duplicate class strings.

## What the first two rewrites taught (2026-10-15, step 3)

**todo** is a terminal application (std/term), so std/ui does not apply to
it; its goal was persistence. Its list is now a durable field,
`Live.field Live.Always @Model.items`, restored with `Live.restore`, taken
as a snapshot with `Live.start` and written by the save command with
`Live.flush` into an append-only kvlog: every change is one record, the
file is the list's history, and no path or handle lives in the model (the
command closes over the store). The terminal check reads the field's last
record. The descriptor machinery (`field`, `restore`, `start`, `flush`)
lives in std/live, which a terminal app has no other reason to import: it
wants a module of its own (`std/durable`), with std/live using it.

**logbook**'s view is std/ui end to end: `page`, `vstackWith` (the client
state declared on the reading column), `hstack`, `card`, `label`/`text`,
`input`, `button`, `keyed`, `space`, `none`. Its own `element`, `input`,
`inputAppearance` and `btn`-with-fourteen-declarations helpers are gone;
`btn` is one line over `UI.button`. The page serves with 133 atomic
utilities and no class string. Its durable field (`nextId`) and the store
were already as the design says.

What std/ui was missing, added for logbook:

- `Fill.Reading`: the reading column (capped, centred), a layout word for
  what was `MaxWidth 640, MarginX Auto, Width 100%` in the app.
- `Field.placeholder`, and the input's focus ring, resize and outline as
  part of the lowering, not the app's.
- `Txt.pre` (keep line breaks) and `Txt.hideEmpty` (hide while the slot is
  empty, std/view's `data-hide-empty`).
- `Btn.tall` (a 44px target for a phone's thumb) and `Kind.Chip` (a tag).
- `none`: the node a branch renders when it has nothing to show.

What std/view is missing, seen from here: a typed send that carries TWO
client fields (`"tags,draft"` is still a raw `G.OnClick (G.wireOpen ..)`
with a comma list, the one string left in logbook's view); a typed
`placeholder`/`rows` attribute (std/ui lowers them to `G.Att`).

Not verified in a browser: `tests/std/logbook_ws.py` fails on the
committed logbook as well (a decode error on the first frame, after the
wire change of 2026-10-14), so logbook was checked by serving it, fetching
the page (every section, input and button present, no `btn`/`inp` class,
keyed `entries`) and `--replay`. The websocket harness is the next thing to
repair.
